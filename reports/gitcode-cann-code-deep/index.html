1算子复现部署

任务：复现 cann-samples 的 vector_add，并确认样例能否成为后续改造起点。

cann-samples环境断点代码审视运行尝试受阻
问题判定

不是样例代码不够，而是仓库没有先回答“我的机器能不能跑”。开发者第一步失败时无法定位是工具、环境、硬件还是代码问题。

这一步具体干了什么
用户目标像真实开发者一样，先把 vector_add 在本地复现，确认仓库样例是否能作为后续改造起点。
查看资产cann-samples/README.md、vector_add/main.asc、CMakeLists.txt、cmake/ascend.cmake。
实际动作按 README 尝试 cmake -S . -B build -DNPU_ARCH=dav-2201，并追到 CMake 对 Toolkit 路径的依赖。
结果与断点本机 cmake 不在 PATH；继续往下还会需要 ASCEND_HOME_PATH、Bisheng 和 NPU 环境。
运行命令与真实环境断点
# cann-samples README 的运行路径 source ${install_path}/ascend-toolkit/set_env.sh cmake -S . -B build -DNPU_ARCH=dav-3510 cmake --build build --target vector_add ./build/Samples/0_Introduction/vector_add/vector_add # 本次本机实测 $ command -v cmake zsh: command not found: cmake $ python3 --version Python 3.9.6 $ echo $ASCEND_HOME_PATH <unset> # ascend.cmake 后续还会解析 ASCEND_DIR / ccec_compiler/bin/bisheng / toolkit headers
cann-samples/README.md
Samples/0_Introduction/vector_add/main.asc
Samples/0_Introduction/vector_add/CMakeLists.txt
cmake/ascend.cmake

问题拆解

  • 代码资产本身有帮助：vector_add 同时包含 kernel、ACL host 侧内存管理、kernel launch、CPU golden 校验。
  • 复现入口没有形成预检脚本。实际运行第一步卡在 cmake 缺失；即便补 cmake，ascend.cmake 还会要求 ASCEND_HOME_PATH 或默认 Toolkit 路径。
  • 问题不是“网页找不到”，而是代码仓缺少环境可执行性检查：开发者无法在 30 秒内知道自己缺 cmake、Toolkit、Bisheng、NPU 还是 Python 依赖。

2算子迁移部署

任务：从学习样例迁移到 asc-devkit / 正式工程，判断是否有“样例到工程”的桥。

asc-devkitcann-learning-hub代码审视

学习代码、API 说明、正式仓结构彼此断开；用户无法把一个能跑的 demo 直接升级成可贡献、可测试、可维护的正式算子工程。

用户目标把学习阶段的 add_custom / vector_add 迁移成更接近正式贡献的 ASC 算子工程。
查看资产asc-devkit API 分层、clangd 配置、examples，以及 cann-learning-hub 的 add_custom 和贡献教程。
实际动作沿“课程代码 -> devkit API -> 正式仓贡献说明”查找是否有生成 op_api/op_host/op_kernel/tests 的脚手架。
结果与断点只找到分散说明，没有找到从样例工程迁移到正式算子结构的一键路径或最小模板。

5泛化 shape 算子实现

任务：从样例和正式仓中找 shape 泛化、tail tile、tiling 数据结构的实现证据。

tilingshape代码审视
问题判定

课程已经补齐工程化和泛化 tiling 概念，但课程、样例、正式仓的代码形态没有被串成可运行的升级提交。用户仍要自己完成从 tail tile 到 TilingContext 的工程映射。

这一步具体干了什么
用户目标把固定/简单长度样例升级为可处理泛化 shape 的算子，确认 tiling 学习路径是否连续。
查看资产vector_add/main.asc 的 tail tile 逻辑，以及 stateless_random_normal_v2_tiling_arch35.cpp 的正式 tiling。
实际动作对比 totalLength/tileNum/tailTileElementNum 与 TilingContext/workspace/blockDim/tilingKey，并检查 learning-hub 3.4/3.5 是否覆盖中间概念。
结果与断点课程覆盖概念，但没有提供同一算子的“课程版本 -> 正式仓提交”的可运行对照工程；工程映射仍要开发者自行完成。

  • 仓库确实提供了 shape 泛化所需代码：样例有 totalLength / tailTileElementNum，正式仓有 tiling context、workspace、tilingKey、blockDim。

  • UT 有 smoke / shape / dtype 异常场景，但没有被直接绑定到“泛化 shape 开发 checklist”，也没有从课程练习自动派生。

6特定 shape 性能优化

任务：查看针对特定 shape 或特定模式的性能优化代码是否能指导开发者做取舍。

性能样例丰富未上板实测代码审视
问题判定

性能 story 有内容，但不是决策系统。开发者看到很多优化版本，却不知道自己的 shape 该先测哪一版、怎么判定瓶颈、如何复现实验。

用户目标找一个具体 shape 或模式的优化参考，看能否从样例判断该先优化访存、分块、SIMT 还是矩阵模板。

问题判定

泛化性能能力很强，但选择逻辑埋在 handler 代码里。对开发者来说，它更像专家实现，不像可解释、可调参、可验证的工具。

问题责任归属

文档问题

说明和解释层

课程并不缺失；缺的是课程代码到正式工程的可运行交接、样例到正式仓的迁移 diff、性能模板选择条件的用户化解释。
应交付：7 阶段任务教程、跨仓交接提交、变更影响面说明、shape/perf 决策说明、TTK 用例编写示例。
结构/框架问题

仓库、工具、脚手架

没有 sample fork / op scaffold / doctor / TTK 自动用例生成；版本与 SoC 配套未形成跨仓锁定；测试和性能工具没有嵌入开发主链路。
应交付：CLI 脚手架、环境与版本预检、正式算子模板、TTK 集成、profiling 集成、结果回写。
体验设计问题

路径编排和工作台

用户按仓库找材料，而不是按任务完成开发；代码资产多但缺少“我现在在哪一步、下一步该做什么”的旅程感。
应交付：算子开发工作台、7 阶段进度视图、改动面地图、shape advisor、失败诊断面板。

一句话结论

CANN GitCode 的真实代码资产并不薄，learning-hub 也已有从基础到性能的学习主线；当前体验问题是课程、样例、正式算子、测试和性能模板没有形成带版本配套的可执行交接。 下一步不应继续只优化页面入口，而应围绕算子开发 7 阶段补跨仓工程交接、脚手架、环境/版本预检、变更地图、测试联动和性能决策工具。
