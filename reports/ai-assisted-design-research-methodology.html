The design problem

面对变化快、信息散、设计难以承接真实工作的分析难题

产品、技术、用户反馈与案例持续出现，但它们常以孤立材料存在；设计讨论容易回到经验判断，方案也难以保留证据、约束与后续验证路径。

SCATTERED外部动向、资料、产品体验与用户经验分散，无法形成持续理解。
DETACHED竞品观察停在功能罗列，尚未进入真实任务、关键决策与异常恢复。
UNCERTAIN研究结论、方案取舍与 Demo 缺少可回溯的证据和明确的验证条件。
RESET每个项目重新搜集材料，已有判断、资产与经验无法被下一个项目继续使用。

研究从领域任务出发，持续接入外部变化；设计方案保留来源、判断和验证指标，并在后续工作中复用。

Measurement framework

用四组指标衡量方法论带来的设计效能与用户结果

RESEARCH COVERAGE

研究覆盖度

重点角色、任务、场景与证据的覆盖率；每个关键结论有来源、时间、版本和条件。

DESIGN TRACEABILITY

方案可追溯度

进入方案的重点问题中，能够回溯到任务和证据、且明确验证指标的比例。

DECISION VELOCITY

决策推进效率

从研究启动到形成可讨论方向的周期；被复用的知识和资产比例；重复搜集材料的时间。

TASK OUTCOME

用户任务结果

上线后目标任务的完成率、完成时间、错误/求助率、恢复时长与关键满意度变化。

MEASURE 先记录当前基线，再按领域选择目标值，以月度或版本为周期观察变化；研究与方案指标用于改进工作方式，用户任务指标用于判断设计是否真正产生效果。

Domain packages

领域研究从四类方法包展开

RESEARCH
DEVEX / DEVELOPER EXPERIENCE

开发者：围绕“把开发任务做成”建立研究

SCOPE
选择 → 配置 → 开发 → 调试 → 协作 → 升级官网、文档、SDK、样例、代码仓、Issue 与社区置于同一段开发活动中理解。

开发者需要理解技术、配置环境、使用工具和接口、调试运行结果、与团队协作，并在问题出现时获得可信的帮助。研究围绕任务能否推进、知识能否执行、版本能否配套、异常能否恢复展开。

设计出口：开发者门户、任务型文档、环境助手、调试与诊断工具、版本治理、支持与社区承接。
OPS / SYSTEM OPERATIONS

运维：围绕“在风险中保持系统可控”建立研究

SCOPE
接入 → 部署 → 观测 → 定位 → 恢复 → 复盘控制台、日志、告警、配置、Runbook、权限、工单和协作机制共同决定工作可靠性。

运维人员配置资源、部署服务、监控运行状态、响应告警、判断影响、定位根因、恢复服务并留下可复用的经验。研究关注发现、判断、定位、恢复与交接是否形成可靠闭环。

设计出口：运维工作台、告警与诊断体验、恢复流程、自动化机制、跨角色协同与知识沉淀。
CLOUD SERVICE

云服务：围绕“将云能力安全、经济地交付给业务”建立研究

SCOPE
选型 → 开通 → 配置 → 部署 → 治理 → 优化服务目录、资源配置、权限、账单、可观测性、SLA 与支持共同构成云服务体验。

云服务研究覆盖理解服务能力、选择规格、创建资源、部署业务、控制成本、治理权限、处理异常和优化资源的全过程。不同角色围绕自助、风险、效率和可见性展开协作。

设计出口：服务门户、资源选型与配置、成本治理、权限协作、可观测性与服务恢复体验。
ENTERPRISE COLLABORATION

企业业务与协作：围绕“多角色共同完成业务交付”建立研究

SCOPE
发起 → 分工 → 审批 → 执行 → 交接 → 复盘角色工作台、数据、权限、流程、通知、协作记录和服务机制共同承接组织任务。

企业业务与协作研究关注不同角色如何共享信息、分配责任、处理例外、完成审批和持续推进交付。重点在于任务状态、协作边界、业务流程与数据可见性。

设计出口：角色工作台、业务流程、状态与责任协同、异常处理、数据可见性与服务编排。
Method package anatomy

每个领域方法包都要写清任务、证据、判断与设计出口

RESEARCH
TASK UNIVERSE

从工作生命周期展开

任务体系覆盖用户从开始工作、做出决策、执行、遇到例外、恢复，到协作与长期演进的完整活动。

EVIDENCE MIX

从可接触条件选择材料

可操作的产品保留真实路径；手册、视频、源码、配置、Issue、案例和用户经验共同补充工作方式。

DESIGN EXIT

从问题类型决定方案形态

入口问题发展为信息架构；知识问题发展为内容与助手；协同问题发展为流程、权限和服务机制。

开发者领域的关键判断

开发者在特定版本、硬件和框架条件下，完成技术任务并稳定复现结果的过程。

  • SUCCESS 环境是否配套、代码是否能跑、结果是否可验证。
  • FRICTION 入口、文档、示例、版本、工具和支持在哪一步增加了不确定性。
  • RECOVERY 出错后是否能定位、获得可信解释、执行修复并带回主路径。

运维领域的关键判断

运维人员在时间压力和风险约束下发现异常、判断影响、定位根因、恢复服务并沉淀经验的过程。

  • OBSERVE 指标、日志、链路与告警能否共同呈现可理解的状态。
  • CONTROL 配置、权限、自动化、回滚和人工接手是否具备安全边界。
  • HANDOFF 多角色能否共享事实、责任、进度和可复用的 Runbook。
