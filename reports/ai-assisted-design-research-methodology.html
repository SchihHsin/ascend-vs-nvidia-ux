02 / 04
DEVEX / DEVELOPER EXPERIENCE

开发者：围绕“把开发任务做成”建立研究

SCOPE
选择 → 配置 → 开发 → 调试 → 协作 → 升级官网、文档、SDK、样例、代码仓、Issue 与社区置于同一段开发活动中理解。

开发者需要理解技术、配置环境、使用工具和接口、调试运行结果、与团队协作，并在问题出现时获得可信的帮助。研究围绕任务能否推进、知识能否执行、版本能否配套、异常能否恢复展开。

设计出口：开发者门户、任务型文档、环境助手、调试与诊断工具、版本治理、支持与社区承接。
OPS / SYSTEM OPERATIONS

运维：围绕“在风险中保持系统可控”建立研究

SCOPE
接入 → 部署 → 观测 → 定位 → 恢复 → 复盘控制台、日志、告警、配置、Runbook、权限、工单和协作机制共同决定工作可靠性。

运维人员配置资源、部署服务、监控运行状态、响应告警、判断影响、定位根因、恢复服务并留下可复用的经验。研究关注发现、判断、定位、恢复与交接是否形成可靠闭环。

设计出口：运维工作台、告警与诊断体验、恢复流程、自动化机制、跨角色协同与知识沉淀。

TASK UNIVERSE

从工作生命周期展开

任务不是功能清单。它覆盖用户从开始工作、做出决策、执行、遇到例外、恢复，到协作与长期演进的完整活动。

EVIDENCE MIX

从可接触条件选择材料

能操作时保留真实路径；不能操作时通过手册、视频、源码、配置、Issue、案例和用户经验重建工作方式。

DESIGN EXIT

从问题类型决定方案形态

入口问题发展为信息架构；知识问题发展为内容与助手；协同问题发展为流程、权限和服务机制。

开发者领域的关键判断

开发者是否能在特定版本、硬件和框架条件下，把一个技术任务完成并稳定复现。

  • SUCCESS 环境是否配套、代码是否能跑、结果是否可验证。
  • FRICTION 入口、文档、示例、版本、工具和支持在哪一步增加了不确定性。
  • RECOVERY 出错后是否能定位、获得可信解释、执行修复并带回主路径。

运维领域的关键判断

运维人员是否能在时间压力和风险约束下发现异常、判断影响、定位根因、恢复服务并沉淀经验。

  • OBSERVE 指标、日志、链路与告警能否共同呈现可理解的状态。
  • CONTROL 配置、权限、自动化、回滚和人工接手是否具备安全边界。
  • HANDOFF 多角色能否共享事实、责任、进度和可复用的 Runbook。

运维复盘与预防将一次事故转化为新的规则、自动化和团队经验。事故复盘、变更记录、知识库、容量数据、权限审计和任务历史。复盘模板、规则回写、自动化建议、经验检索与演练路径。
USE同一类任务在不同竞品或不同生态中对齐比较；问题问法、前置条件和期望产出保持等价，差异才可归因到产品、内容、工具或服务机制。

规范 skill 的输入

Demo 的任务目标、用户路径、已有信息架构、品牌/产品定位、可用组件、内容与状态要求。规范 skill 在这些约束上工作，而不是脱离场景重新发明方案。

  • INPUT 研究命题、Demo、设计系统、真实内容与边界。
  • PROCESS 统一层级、布局、颜色、组件、状态和内容表达。

规范 skill 的输出

更完整的 Demo 表达：清晰的主次、可复用的结构、真实的空态与异常、可交接的组件和说明。它让方案从“概念可讨论”发展为“设计语言中可继续推进”。

  • OUTPUT 页面、组件、状态、交互说明与视觉规范对齐。
  • MEMORY 设计资产回写知识库，保留来源任务与选择理由。
