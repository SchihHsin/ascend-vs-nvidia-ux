问题定义

GitCode 上的 CANN learning hub 与 CANN 组织仓库，能否承担「开发者学习入口 + 开源生态索引 + AI 可检索知识库」这三重角色？

不是在评估什么

不是泛泛评价 GitCode UI，也不是复刻官网竞品分析。这里看的是 CANN 内容迁入 GitCode 后，能不能成为开发者和 AI 的下一层承接。

用户是谁

第一次认真做 Ascend C / 自定义算子的开发者，知道目标但不知道先看哪门课、进哪个仓、如何在线或本地跑、怎么测试、去哪练习和贡献。

成功标准

能完成「找入口 → 学路径 → 跑第一个算子 → 进阶开发 → 测试验证 → 看样例/模板 → 练题 → 反馈/贡献」的完整闭环。

05

结论与方案 Demo：每个问题都要落成一个可改的界面/内容模块

总判断：不是资料少，而是“下一步”没有被产品化

18 个触点和 5 个 AI benchmark 问句共同指向同一个问题：CANN GitCode 已经有课程、Notebook、工程仓、测试工具、样例库、题库和贡献入口，但它们没有被组织成连续任务路径。下面把结论和对应 demo 放在同一张卡里，避免“分析很多、方案很少”。

S1入口承接

learning hub 要从代码仓首屏变成算子开发任务首页

人类用户会把 learning hub 当成代码仓；AI 虽能抓到 README，但生成答案时会把入口、路线和运行方式混在一起。

来自
T1/T2；AI Q1。搜索能带来用户，但首屏没有马上回答“我现在该点哪里”。
应做
首屏先给任务入口，再给文件树。主 CTA 应覆盖在线体验、本地运行、学习路线、测试验证和工程开发。

S2学习路径

README 内容够厚，但需要把“推荐顺序”产品化

用户和 AI 都能找到内容，但都要推断哪些是必做、哪些是进阶、哪些受硬件限制。

来自
T3/T5；AI Q2 最高 4.6。课程体系强，覆盖基础、Tiling、调试、msProf。
应做
把课程按目标和难度重排：入门必做、工程必做、性能选学、贡献前置，并写明耗时和限制。

T4/T6；AI Q1 的步骤可复现只有中档。入口强，但登录/启动状态打断首跑。
应做
把账号要求、资源状态、预计耗时、本地替代命令和 Issue 反馈做成启动页固定模块。

06

行动优先级

总判断：GitCode CANN 已经有内容资产，下一步要做“路径产品化”

本轮完整跑完后，最重要的发现不是“CANN 算子开发资料少”，而是相反：资料、Notebook、在线环境、练习平台、工程仓、测试工具、模板库、样例库和正式算子库已经有一批了。真正影响体验的是这些资产没有被组织成一个可立即行动的开发者路径，也没有被组织成一个 AI 稳定可引用的任务图谱。

P0
先做 learning hub 首屏重构：把仓库首页改造成任务入口。
首屏放 5 个明确动作：① 10 分钟在线体验 ② 本地运行命令 ③ 完整学习路线 ④ 测试验证入口 ⑤ 进入 asc-devkit 工程开发。文件列表和运营指标可以后置。
learning hub / 官网平台
P0
给在线体验补“失败兜底路径”，否则 10 分钟承诺会反噬。
登录前说明资源和限制；启动失败时给出原因、重试入口、登录要求、本地 clone + 执行命令。不要让用户停在一个泛化登录弹窗。
AtomGit AI / CANNLab
P1
做 CANN 算子开发仓库地图，解决“我该看哪个仓”。
按任务而非仓库名组织：入门学习 learning hub；工程开发 asc-devkit；验证 ops-test-kit；模板 catlass；样例 cann-samples；算子库 ops-nn/ops-math/ops-transformer；练习 CANNJudge；反馈 Issues/Roadmap。
CANN 开源运营
P1
把 AI 友好当成内容发布标准。
每个核心仓 README 顶部固定四块：适用场景、版本/硬件限制、最短可运行步骤、相关仓库。这样开发者更快理解，AI 也更少胡乱推断。
资料 / 生态内容
P2
把“学-练-赛-贡献”做成闭环指标，而不是分散链接。
每个教程末尾指向下一步：练一道 CANNJudge 题、看一个 asc-devkit 样例、提交 issue/PR、进入 Roadmap。让用户完成一次小闭环，而不是只读完一页。
