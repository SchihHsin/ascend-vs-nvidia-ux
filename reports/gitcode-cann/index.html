01

问题定义

基于 GitCode 上这些 CANN 仓库，开发者能否从“看懂一个 Ascend C 自定义算子”走到“本地工程开发、编译运行、测试验证、性能优化和反馈贡献”？

不是在评估什么

不是泛泛评价 GitCode 界面，也不是看资料是否容易点到。这里看的是仓库内容是否足以支撑真实 Ascend C 算子开发：代码怎么落到工程、怎么编译、怎么验证、怎么调优、怎么贡献。

用户是谁

第一次认真开发 Ascend C 自定义算子的开发者，目标不是“逛资料”，而是要在本地或在线环境里写出一个算子，接入工程，跑通验证，再找到可复用样例或贡献路径。

成功标准

能完成「选定算子任务 → 找到最小工程 → 编译运行 → 接入测试 → 对比 Golden → 看样例/模板优化 → 练题或提交反馈」的开发闭环。

为什么是这些仓库：按一个具体开发任务反推，不是仓库清单巡检

本轮以“开发一个 Add / 向量类 ASC 自定义算子”为样例任务：先从 learning hub 跑通第一个 Notebook，再把代码迁到本地 asc-devkit 工程，接入 ops-test-kit 做 Golden / 性能验收，之后再判断是否复用 cann-samples / catlass，或进入 ops-* 正式算子库贡献。CANN org 只用于发现候选仓；不在这条开发任务链上的仓库没有展开评分。

为什么用

02

这次具体抓到了什么

下面这些不是推断，而是本轮围绕“开发一个 Add / 向量类 ASC 自定义算子”这个任务，在 GitCode 页面、README、目录页和截图中实际抓到的内容颗粒。它们说明：CANN 资料不是空的，真正的问题是这些证据没有被组织成开发任务所需的工程闭环。

E1

learning hub 已有版本与课程事实

抓到
README 写明支持 CANN 9.0.0，并展示教程、示例、优化方案和在线互动运行。
问题
这些信息没有汇成“最小 ASC 工程”的固定卡片。
E2

Ascend C 系列目录非常细

抓到
目录包含 HelloWorld、kernel 函数、泛化 Tiling、CPU/NPU 调试、msProf 性能分析等章节。
问题
章节按知识点排布，未按写 kernel、调试、验收、调优的开发动作排布。
E3

在线 Notebook 链接数量足够

抓到
Ascend C 目录页中“在线体验”出现 82 次，且链接带 repoUrl、path、scanFilePath。
问题
在线能跑不等于本地能开发，缺本地等价工程、CMake 和输入输出说明。
E4

硬件限制能抓到，但不够产品化

抓到
Ascend C 系列页提示当前仅针对 Atlas A2 系列验证，其它产品可能存在问题。
问题
该限制没有固定沉淀到每个样例、命令和 AI 可读摘要里。
E5

CANN org 抓到 68 个项目

抓到
组织页显示全部项目 68 个，首屏能见 hcomm、ops-*、asc-devkit、ops-test-kit、catlass、cann-samples 等。
问题
列表能说明“有什么”，不能说明“开发 ASC 算子下一步该用哪个”。
E6

asc-devkit 是真实工程承接点

抓到
README 覆盖 API 层级、目录结构、快速入门、clangd/IDE、相关资源和 Roadmap。
问题
缺 Notebook 样例到 asc-devkit 工程的目录映射和调试配置迁移。
E7

ops-test-kit 具备验收能力

抓到
仓库内容围绕 Golden、批量测试、性能验证、编译运行等关键词展开。
问题
它没有被教程声明为“写完 kernel 后必须进入的验收步骤”。
E8

正式算子库有版本和贡献信号

抓到
ops-nn 等仓包含版本配套、环境准备、源码下载、学习教程、贡献指南和 Issues。
问题
缺“新开发者可以学什么、复用什么、提交什么”的边界说明。

总判断：不是资料少，而是 Add / 向量类算子的开发动作没有被工程化串起来
