CANN GitCode 算子开发代码级体验评测

本次评测把开发者目标收窄为“基于 GitCode CANN 仓库实际完成 ASC / Ascend C 算子开发”，按 7 个开发阶段模拟真实行动： 找代码、改代码、接构建、接测试、看正式算子结构、读 tiling / kernel / API 实现、尝试运行，并记录断点。

核心问题先看这里

这次代码级评测最重要的结论不是“仓库有没有内容”，而是“内容没有把开发者带到完成”。下面 6 个问题会直接影响开发者基于这些仓库开发 ASC / Ascend C 算子。

P0 · 任务链断裂
1→7

代码资产多，但没有一条端到端开发主线

课程、样例、API、正式算子、测试、性能模板分散在多个仓，用户要自己拼“下一步该去哪”。

影响：开发者能找到局部答案，但很难从复现样例连续走到正式算子修改、测试和性能优化。
P0 · 环境闸门
>_

环境失败太早暴露，且无法自诊断

实际构建第一步卡在 cmake 缺失；TTK 卡在 numpy 缺失；后续还依赖 Toolkit、Bisheng、NPU。

影响：用户还没进入 ASC 代码问题，就已经不知道是工具链、依赖、硬件还是代码导致失败。
P0 · 工程化桥缺失
{ }

从样例到正式算子仓没有脚手架

我能手动从 vector_add 改出 vector_sub，但要自己改 target、install path、README、父级 CMake。

影响：基本功能实现可学，但迁移到 op_api / op_host / op_kernel / tests 的正式结构时容易断。
P1 · 改动面不透明
MAP

builtin 定制不知道最小必改集合

正式算子横跨接口定义、shape/tiling、kernel、ACLNN 参数校验、UT，多目录协作但缺变更地图。

影响：加 dtype、加 shape、改属性时，用户不知道漏改哪个文件会导致编译、运行或注册失败。
P1 · 泛化 shape 跳层
N→*

简单 tiling 到正式 tiling 的抽象跨度太大

样例里是 totalLength / tailTileElementNum，正式仓是 gert::TilingContext / tilingKey / workspace / blockDim。

影响：用户能看到两端代码，但缺“同一算子逐步升级”的中间层。
P1 · 性能决策黑箱
SPD

性能模板强，但选择规则埋在代码里

CATLASS 有 dynamic tiling 和 handler 选择，cann-samples 有性能 story，但没有 shape advisor。

影响：用户知道有 StreamK、SplitK、padding、swizzle，却不知道自己的 MNK/layout 应该先试哪条路径。

逐阶段代码分析

1算子复现部署

任务：复现 cann-samples 的 vector_add，并确认样例能否成为后续改造起点。

cann-samples环境断点代码审视运行尝试受阻
问题判定

不是样例代码不够，而是仓库没有先回答“我的机器能不能跑”。开发者第一步失败时无法定位是工具、环境、硬件还是代码问题。

README 给出：source ${install_path}/ascend-toolkit/set_env.sh cmake -S . -B build -DNPU_ARCH=dav-3510 或 dav-2201 cmake --build build --target vector_add ./build/Samples/0_Introduction/vector_add/vector_add
cann-samples/README.md
Samples/0_Introduction/vector_add/main.asc
Samples/0_Introduction/vector_add/CMakeLists.txt
cmake/ascend.cmake

问题拆解

  • 代码资产本身有帮助：vector_add 同时包含 kernel、ACL host 侧内存管理、kernel launch、CPU golden 校验。
  • 复现入口没有形成预检脚本。实际运行第一步卡在 cmake 缺失；即便补 cmake，ascend.cmake 还会要求 ASCEND_HOME_PATH 或默认 Toolkit 路径。
  • 问题不是“网页找不到”，而是代码仓缺少环境可执行性检查：开发者无法在 30 秒内知道自己缺 cmake、Toolkit、Bisheng、NPU 还是 Python 依赖。

问题拆解

  • 对基本功能实现，代码样例是有效的。开发者可以复用内存申请、拷贝、tiling、launch、CPU 校验骨架，只改计算语义。

  • 运行没有完成不是因为源码无法改，而是当前环境缺 cmake 和 CANN 工具链。报告应把“代码可改”和“环境不可跑”分开判断。

任务：读 CATLASS dynamic optimized matmul，判断泛化性能优化是否可学、可迁移。

catlass动态模板选择代码审视
问题判定

泛化性能能力很强，但选择逻辑埋在 handler 代码里。对开发者来说，它更像专家实现，不像可解释、可调参、可验证的工具。

问题拆解

  • 泛化性能优化的底层代码很有价值：它把 runtime shape、layout、padding、splitK、streamK、tilingKey 和 kernelSerial 串起来。
  • 但对开发者而言，这些知识被埋在模板代码中。README 说“尽力获取最优性能，但不保证最优”，却没有给出可操作的 shape 覆盖矩阵和失败兜底策略。
  • 要变成可用体验，需要把 handler 选择规则可视化，让开发者输入 MNK/layout 后看到选择了什么、为什么、下一步该测什么。

分析结论与 demo 改进

下面不是把结论和 demo 分开，而是每条结论直接带问题、代码证据、责任归属和可落地的界面/工具 demo。

结论 1：最大问题不是“有没有代码”，而是代码资产没有被编排成任务闭环
体验设计/路径编排结构/框架
  • 证据：课程、样例、devkit、正式算子、测试工具、性能模板都存在，但开发者要跨 6 个仓自己拼路径。
  • 影响：从 vector_add 到正式 builtin 修改，中间缺“生成工程 -> 改动文件 -> 编译 -> TTK -> profiling”的主线。
  • 建议：建设“算子开发任务工作台”，按 7 阶段聚合代码入口，而不是按仓库/页面入口组织。

问题责任归属

文档问题

说明和解释层

样例到正式工程的迁移教程不足；泛化 shape / tiling 从简单样例到正式仓的桥接不足；性能模板选择条件没有用户化解释。
应交付：7 阶段任务教程、变更影响面说明、shape/perf 决策说明、TTK 用例编写示例。
结构/框架问题

仓库、工具、脚手架

没有 sample fork / op scaffold / doctor / TTK 自动用例生成；测试和性能工具没有嵌入开发主链路。
应交付：CLI 脚手架、环境预检、正式算子模板、TTK 集成、profiling 集成、结果回写。
体验设计问题

路径编排和工作台

用户按仓库找材料，而不是按任务完成开发；代码资产多但缺少“我现在在哪一步、下一步该做什么”的旅程感。
应交付：算子开发工作台、7 阶段进度视图、改动面地图、shape advisor、失败诊断面板。

一句话结论

CANN GitCode 的真实代码资产并不薄，甚至在样例、正式算子结构、性能模板上有明显积累；当前体验问题是这些代码资产没有被组织成“开发者能连续完成任务”的工程化旅程。 下一步不应继续只优化页面入口，而应围绕算子开发 7 阶段补脚手架、预检、变更地图、测试联动和性能决策工具。
