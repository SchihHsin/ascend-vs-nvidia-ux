判断 1 · 一个算子开发是 5 次搜索的串联，被最弱、又最靠前的「写 kernel」拖着
核心一问：开发一个算子，AI 的可用性是一个数，还是一路在变？

开发一个算子不是搜一次，是沿时间撞上 5 次搜索：写 kernel(D) → Tiling(M) → 内存越界(X) → 注册集成(O) → 精度排查(L)。可用性一路在变，不是一个数。

5 次里 4 次官方都抓得到（M.63 / X.74 / O.72 / L.69，各有版本/第三方平台的小坑），只有写 kernel 的 D 官方真受阻（.41）。但整条路的体感被 D 拖着——因为它又最弱、又最靠前：kernel 写不出，后面 Tiling/编译/精度全建在第三方平台地基上，到编译才报错。场景可用性 ≈ 最弱且最靠前的那一搜。

怎么改：优先修最靠前的瓶颈——把写 kernel 那页（opdevg）静态化（治本，见 19）；在此之前，AI 抓取为空时显式报「官方未取得、以下第三方平台」，别让错误地基静默往下传。

判断 2 · 真正卡住 D 的不是「技术难」，是人机「交接」的质量
核心一问：一次 D 开发，AI 和人交接了多少次？哪里最容易出问题？

时序图数得出来：全旅程人机交接约 8–10 次（AI 给 → 人执行 → 报错回灌 → AI 解读 → 人重试…），且编译 / 部署段（P5）交接最密。这是横截面给不出的「协同密度」。

每一次交接都是一道信息可能丢失的关口：AI 给的命令带占位、人填错；人回灌的报错不全、AI 解读偏。卡的不是「算子难写」，是这条人机流水线的接口质量——交接越密的地方（P5），出错越多。

怎么改：把交接做成产品的一等公民——AI 主动标「这里要你填什么」、报错能一键完整回灌、每个交接点留 checkpoint。把摩擦从「人自己扛」变成「产品接住」。

判断 3 · 体感「前松后紧」：AI 在检索段给虚假信心，落地段把人独自留下
核心一问：开发者走完这条路，「顺 / 难」的体感曲线是什么形状？

把旅程当一条体感曲线：前段（检索 / 起草）AI 很顺、很能干，给人「这件事 AI 能完成」的虚假信心；后段（编译 / 部署 / 精度）越来越是人独自承担，AI 退成旁边解读报错的副驾。

曲线最低点是 A 类决策（soc_version / 版本 / 精度）——AI 够不着本机 / 业务事实、只能猜，恰好都落在后半段：前面越顺，这里落差越大。真正的风险不是「AI 不行」，而是「先让你以为可行、到高难度场景才发现得自己来」。

怎么改：把这条落差曲线显式化——旅程一开始就告诉用户「这条路后段有 3 处只能你来（要本机芯片 / 版本 / 业务阈值）」，别让落差到高难度场景才暴露。

判断 1 · 换个场景，「逐段曲线」就从深谷变成平稳波动——可用性是任务相关的
核心一问：同一套 AI，换到训练场景，这条逐段可用性曲线长什么样？

训练也是 5 次搜索的串联，但和算子开发是两种地形：5 搜里官方全部抓得到（②全 4），最弱的 F 分布式也有 .72（中高）、只是版本散；没有 D 写 kernel 那种 .41 受阻、又最靠前、把全程拖下水的深谷。

连第三方平台这条线在两个场景里的角色都不同：D 是「官方塌了被迫转第三方平台、第三方平台还薄」（受阻兜底）；训练是「官方够用、第三方平台再添 ranktable 实例 / 收敛经验」（健康补充）。而且训练里人也直接和昇腾社区交互——去官方配套表 / Gitee 样例对齐版本拓扑、撞 OOM 时自己翻 CSDN 实战贴。同一条线，地形不同、角色就不同。

这正印证「可用性是任务相关的」：越靠采纳漏斗的上手 / 训练侧（迁移、分布式、显存），华为投入越足、官方做得越厚；越往深处自研（写 kernel）越塌。同一个 AI、同样按时间走，体感差一个量级——这是横截面 19 的均值掩盖、只有逐段旅程才显出来的。

怎么改：训练这条路官方都抓得到，治本重点不在「抓不到」而在「版本散」——收口 F/I 的版本（一个 canonical + 配套查询器）最能把 .72 抬起来。

判断 2 · 训练顺，那摩擦在哪？不在「抓不到」，在「版本对齐 + 本机拓扑」
核心一问：既然官方都抓得到，训练落地真正卡人的是什么？

训练的真实摩擦不是文档受阻，是两类 AI 够不着的事实：① 版本对齐——torch_npu 必须与本机已装的 CANN / PyTorch 严格配套，版本号又并存（④散乱），AI 给得了配套表、给不了本机装的是哪个；② 本机拓扑——多卡几张卡、怎么组网，AI 只能给 HCCL 模板。

这跟算子开发的 A 类决策同源（都是本机 / 业务事实回到人），但训练里它们每一处都有官方文档兜着、不叠加受阻——所以是「摩擦」而非「深谷」。真正能被供给侧改善的，正是其中的「版本散」。

怎么改：供给侧收口版本（治根）；使用侧把版本声明前置——开训前先核对本机 CANN / torch_npu 版本，别等 import 失败才发现配错。

判断 3 · 体感是「平稳协同」，不是算子那条「前松后紧」
核心一问：两个场景的体感曲线，差在哪？

把训练当一条体感曲线：全程都是「AI 给方案 → 人按本机调 → 验证」的均匀协同，每段都有官方文档兜着，A 类决策（版本 / 拓扑 / 精度）分散在各段、各自独立，不像算子那样在后半段集中爆发。

所以训练没有「检索段虚假信心 + 落地段独自承担」的落差——它的难是均匀分布的、可预期的。对开发者体感而言：算子开发要管理的是「别被前段的顺骗了」，训练要管理的是「每段都得备好本机事实」。同一个 AI，副驾的称职程度取决于这条路有没有官方兜底。

怎么改：训练侧顺，重点是把每段需要的本机事实清单前置（版本 / 卡数 / 显存 / 精度阈值），让协同更省来回；供给侧继续收口版本即可。

4.1 工具调用策略：为什么是有限次检索，而非更多 / 更少

上图 s2–s4 里 AI 没有把检索工具刷到上限，实测 D 任务只搜了 ~1–2 轮就转入拼装。背后是两层机制叠加：

  • 硬上限 = max_uses：web_search 是 Anthropic Messages API 的服务端工具，注册时带 max_uses 封顶（如 5）；超过会返回 max_uses_exceeded，模型不能无限刷。
  • 软停止 = 模型自主判断「信息已足够」：服务端工具在同一轮内自带 loop——模型决定检索内容 → 平台执行并回灌结果 → 模型判断信息是否足够 → 不足则续检索、足够则停止并生成终答（stop_reason: end_turn；耗时较长会先 pause_turn 再继续）。所以「调用 N 次」不是写死的常量，而是 min(max_uses, 模型判断收敛点)。
  • 为什么 D 任务收敛得早：实测前 1–2 条结果（知乎 / ai6s.net / MindSpore 官方 / CSDN）已能拼出步骤骨架，边际信息递减；继续搜更多只会拿到同质 CSDN 互抄（D 的第三方平台本就薄），模型据此判断「再搜性价比低」→ 提前停。检索次数少 ≠ 偷懒，而是边际收益判断。

输入优化：用户怎么写指令能显著抬升输出精准度

优化手段对这条旅程的具体作用
补约束：写明「要可照抄的完整命令 + 锁定版本号」逼 AI 在 s5 给出带真实 soc_version 占位说明的 msopgen 命令，而非泛泛描述，减少 d1 的来回。
限范围：写明芯片型号 / CANN 版本（如 910B1 + 8.0.RC3）直接消解 d2 版本对齐这个卡点——AI 不必在多版本间猜，输出一次到位。
限渠道：写明「优先官方文档，无法取得则说明受阻、不得编造」触发 AI 在 s3 受阻时诚实标注页面正文未能取回并转第三方平台，而不是用记忆补全一个看似正确、实则无法运行的步骤。
给反馈：把 s9 的编译报错原文贴回AI 解读的准确度直接取决于报错原文，而非「我编译失败了」这类模糊描述。

4.3 Agent 循环架构（图）+ 最小实现代码 示范实现 · 基于公开 Anthropic Messages API，非 Claude 内部源码

「我平常如何运行」的 agent 循环流程：输入（原始问句 + system 约束 → messages，不预处理）→ 模型推理 ①意图解析 → ②子目标拆解 → ③工具路由 → 需要工具?（stop_reason）→ 是：通常先调 web_search 发现官方 / 第三方候选页，再调 web_fetch 进入爬取协议检查——先过 robots.txt 准入门控（禁止则返回 url_not_allowed），通过后 sitemap.xml 经 robots 的 Sitemap: 指令被发现（提供 URL 清单），llms.txt / llms-full.txt 是独立旁路（可选、厂商未确认消费）——三路汇聚到抓取目标正文；正文再经页面解析（HTML → DOM → 语义提取 → 纯文本/Markdown，按文档流顺序读取，标题/代码/列表权重更高，忽略 CSS/JS/广告；SPA 页此步正文 0 字）（已知 URL 时可直接进入检查链）→ tool_result 回灌 → ④ 证据是否充分? → 充分：⑥ 收敛 → 终答；不足：能否继续检索（未达上限且预期有效，则换检索词回 ③ 再检索一轮）。检索穷尽后若仍无可靠证据，模型无法可靠识别「自身不知道」，会凭记忆填补空缺 = 杜撰（看似正确、实则有误）。否（end_turn）则不检索，先进入模型自带知识这条证据链，再参与证据判断。右上角可切「代码」看最小实现（逐段 A–D 对应）。
悬浮任意节点查看该环节职责（锚 D 任务）。web_fetch 内部不是一条直线，而是分叉的协议检查 + 页面解析：先过 robots.txt 准入门控（禁止则 url_not_allowed），通过后 sitemap.xml 经 robots 的 Sitemap: 指令被发现（提供 URL 清单），llms.txt / llms-full.txt 是独立旁路（可选、厂商未确认消费）——三路汇聚到抓取目标正文。正文并非直接可读：HTML 先解析为 DOM，再提取语义块（标题/段落/代码/列表/表格），忽略 CSS/JS/广告，最后转成纯文本/Markdown 输入模型——按文档流顺序读取，标题与代码块权重更高。SPA 页此步正文 0 字（只回导航+meta），是 D 任务受阻的技术根因。自带知识无需检索亦在其中，是第三条证据来源。节点左上角的 P0–P3 是文件优先级（P0 正文主体 / P1 一票否决门控与结构化事实 / P2 发现与语义辅助 / P3 零成本投机）；另有 HTTP 状态码·重定向（P1，位于 robots.txt 之前）与 head 元数据 canonical / JSON-LD（P1，位于解析内部）未入图——完整 12 类文件清单、大模型怎么「读」页面、llms.txt 位置与布局减幻守则见下方 4.4 节。
最小实现代码（A–D 段对应架构图各环节）：
import anthropic
client = anthropic.Anthropic()

# ① 工具注册：web_search 是服务端工具，max_uses 即 §4.1 的硬上限
TOOLS = [
    {"type": "web_search_20250305", "name": "web_search", "max_uses": 5},
    {"name": "web_fetch", "description": "抓取一个 URL 的正文",   # 客户端工具：演示通用 agent 循环
     "input_schema": {"type": "object",
         "properties": {"url": {"type": "string"}}, "required": ["url"]}},
]

def run_agent(user_question):
    # A. 接收并解析用户原始自然语言输入 —— 直接进 messages，模型负责理解
    messages = [{"role": "user", "content": user_question}]

    while True:
        # B. 调度：模型自己决定这一轮是搜 / 抓 / 还是直接答（§4.2 的「规划」）
        resp = client.messages.create(
            model="claude-opus-4-8", max_tokens=4096,
            system="优先给可照抄命令、锁定版本号；官方抓不到就说明受阻，绝不编造。",
            tools=TOOLS, messages=messages)
        messages.append({"role": "assistant", "content": resp.content})

        # C. 终止条件：模型不再要工具 → 收敛、返回终答（对应图 s5 的 end_turn）
        if resp.stop_reason != "tool_use":
            return "".join(b.text for b in resp.content if b.type == "text")

        # D. 多轮循环：执行客户端工具并把结果回灌（受阻时如实标注，不编造 → 图 s3）
        results = []
        for b in resp.content:
            if b.type == "tool_use" and b.name == "web_fetch":
                body = fetch_url(b.input["url"])
                results.append({"type": "tool_result", "tool_use_id": b.id,
                    "content": body or "（页面正文未能取回/robots 拦截）"})
        messages.append({"role": "user", "content": results})
A 段
接收解析用户自然语言：原始问句直接进 messages，不做模板化预处理——理解交给模型本身。
B 段
调度逻辑：每轮 messages.create 让模型自主决定搜 / 抓 / 答。web_search 的多轮在服务端同一次调用内闭环（§4.1 软停止）。
C 段
终止逻辑：stop_reason != "tool_use" 即模型判断信息足够、收敛产出终答——对应图中 s5。
D 段
多轮循环 + 受阻处理：客户端工具结果回灌；抓不到正文时显式写「正文抽不到」而非留空或臆造，这是「绝不编造」铁律在代码层的落点（图 s3 受阻）。
诚实边界：上述为公开 Messages API 的忠实示范，用于解释 agent 循环骨架，不是 Claude 产品的内部源码；服务端 web_search 的内部检索 / 排序实现不可见，这里只能就「对外可观测的调用契约」作解。

4.4.2 大模型怎么「扫描」页面：不是从上到下逐行看，而是整个文本一次性入脑

先纠正一个直觉：web_fetch 这条路径上，模型根本不「看」界面——没有视觉、不逐行扫视、也没有鼠标滚动。真实链路是：

抓回 HTML剥 CSS/JS/广告 → 纯文本/Markdown切成 token 序列一次性整体放进上下文窗口自注意力并行关联
  • 「从上到下」只对了一半——文档流顺序 = 语义顺序。模型不按行读，但 DOM 从上到下映射成 token 从先到后，与视觉顺序基本一致；训练语料的自然顺序让开头的 token 天然承担「引出下文」的角色（先见到标题，才知道后文在讲什么）。
  • U 型位置偏置（lost in the middle）：注意力对开头与结尾最强、中部最弱（Liu et al. 2023, Lost in the Middle: How Language Models Use Long Contexts）。长文档中段的事实最易被忽略或张冠李戴——重要结论别埋长文中段。
  • 截断：超长页面在两个关口被砍——工具返回大小上限 + 上下文窗口。尾部内容可能整段进不了模型，比「被忽略」更彻底。
  • 权重效应发生在解析阶段，不在视觉阶段：标题层级、pre/code、table、列表被识别为高价值语义块；而视觉上的「显眼」（大图、动效、配色）对文本路径零贡献——对人眼的强调不等于对模型的强调。
给站点方的推论：页面的「可读性」要按DOM 语义顺序重新审计一遍，而不是按视觉设计稿——视觉上再醒目的信息，如果 DOM 里是中段一长串无结构文本、或者是 JS 现渲染的，对模型等于不存在。

4.4.3 llms.txt 放哪里：反直觉的答案——页面内位置无所谓

llms.txt 的约定（llmstxt.org 提案）是站点根路径的 /llms.txt 文件，一个纯 Markdown 索引。AI 与取 robots.txt 同款方式直接请求这个 URL，不通过页面内链接发现它，所以：

  • 放在页面顶部、页脚、还是根本不放链接——都不影响 AI 拿不拿得到。AI 是按约定路径直接请求 /llms.txt。
  • 它不是 meta 标签，不写进 <head>；页内 <link> 引用它也没有标准约定。
  • 页脚放一个人可见的链接，价值仅在于人和普通爬虫能发现它。
真正要紧的是三件事：① 根路径可匿名 GET（无登录、无反爬墙）；② 纯 Markdown 低噪内容；③ URL 长期稳定不搬家。再叠一层诚实边界：截至 2026 年，Anthropic / OpenAI 均未正式确认其 API 工具消费第三方 llms.txt，Google 明确忽略——它是零成本投机，不是必答题；真正必答的是 4.4.1 的 P0（正文 SSR 可抓）。

4.4.4 什么样的页面布局能让大模型提效、减幻觉

把 4.4.2 的机制反过来用，就是设计守则——每一条都对得上一个真实幻觉来源（右列锚回 D 任务实测卡点）：

布局 / 结构手段起效机制抑制哪类幻觉
SSR / SSG 直出正文，别 CSR SPA正文直接在初始 HTML 里，解析器拿得到D 根因：SPA 正文 0 字 → 模型只剩记忆 → 杜撰
语义 HTML：<main><article><nav><footer>解析器按标签精准剥噪留主导航 / 页脚噪音挤占 token 与注意力，关键事实被稀释
一页一主题 + 严格 h1>h2>h3 层级语义块边界清晰，标题先于正文被读检索命中页与问题错位（把「产品介绍」当「how-to」用）
命令用 <pre><code>、事实用 <table>高权重语义块、逐字可复制模型凭记忆改写命令（参数 / 路径错）
版本号 / 更新日期显式（如 CANN 8.0.RC3 · 2026-06 更新）给模型锁定证据时效的锚点用旧版本训练知识填新问题（d2 / dVerT 版本对齐卡点）
canonical + 稳定 URL多 URL 同内容去重，正主唯一多版本混叠拼接——幻觉「拼合体」最常见的来源
正文前置（DOM 序）+ 超长页拆分U 型注意力 + 截断对策中段 / 尾部关键事实丢失或被张冠李戴
代码 / 表格禁图片化文本路径拿不到图内文字命令零丢失（OCR 不在 web_fetch 这条路上）
（投机）根路径提供 /llms.txt 索引若被消费则跳过发现层摩擦零成本旁路，非核心依赖
诚实边界：① 4.4.1 的优先级是基于可观测调用契约 + 通用爬取工程惯例的判断排序（「九成价值在 P0+P1」是工程估计，非测量）；② 4.4.2 的扫描机制引用公开研究（Liu et al. 2023 lost-in-the-middle）与自注意力的通用描述，不针对任何厂商内部实现；③ 4.4.4 是机制反推的设计守则，单项收益未做 A/B 测量。
