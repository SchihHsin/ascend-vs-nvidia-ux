②大模型怎么「扫描」页面：不是从上到下逐行看，而是整个文本一次性入脑

先纠正一个直觉：web_fetch 这条路径上，模型根本不「看」界面——没有视觉、不逐行扫视、也没有鼠标滚动。真实链路是：抓回 HTML → 剥 CSS/JS/广告转纯文本 → 切 token → 一次性整体放进上下文窗口，自注意力并行关联。位置不平等（U 型）+ 截断，见图 C。
图 C · 左：页面 DOM 按文档流顺序剥噪、切 token、一次性整体放进上下文窗口——「从上到下」只对了一半（文档流顺序＝语义顺序），但不存在逐行扫视。右：token 位置不平等——开头与结尾注意力强、中段最弱（U 型，lost in the middle），超长页还会在两道上限处被整段截断。设计推论见底部三条。
  • 「从上到下」只对了一半——文档流顺序 = 语义顺序。模型不按行读，但 DOM 从上到下映射成 token 从先到后，与视觉顺序基本一致；训练语料的自然顺序让开头的 token 天然承担「引出下文」的角色（先见到标题，才知道后文在讲什么）。
  • U 型位置偏置（lost in the middle）：注意力对开头与结尾最强、中部最弱（Liu et al. 2023, Lost in the Middle: How Language Models Use Long Contexts）。长文档中段的事实最易被忽略或张冠李戴——重要结论别埋长文中段。
  • 截断：超长页面在两个关口被砍——工具返回大小上限 + 上下文窗口。尾部内容可能整段进不了模型，比「被忽略」更彻底。
  • 权重效应发生在解析阶段，不在视觉阶段：标题层级、pre/code、table、列表被识别为高价值语义块；而视觉上的「显眼」（大图、动效、配色）对文本路径零贡献——对人眼的强调不等于对模型的强调。
给站点方的推论：页面的「可读性」要按DOM 语义顺序重新审计一遍，而不是按视觉设计稿——视觉上再醒目的信息，如果 DOM 里是中段一长串无结构文本、或者是 JS 现渲染的，对模型等于不存在。

③llms.txt 放哪里：反直觉的答案——页面内位置无所谓

llms.txt 的约定（llmstxt.org 提案）是站点根路径的 /llms.txt 文件，一个纯 Markdown 索引。AI 与取 robots.txt 同款方式直接请求这个 URL，不通过页面内链接发现它。
图 D · 左：链接放顶部 / 页脚 / 不放，三种放法 AI 都照样拿得到——它不通过页面发现 llms.txt。中：AI 与取 robots.txt 同款方式直接 GET 根路径的 /llms.txt（它是文件，不是页面元素）。右：真正决定成败的是三件事：可匿名 GET、纯 Markdown、URL 稳定。
  • 放在页面顶部、页脚、还是根本不放链接——都不影响 AI 拿不拿得到。AI 是按约定路径直接请求 /llms.txt。
  • 它不是 meta 标签，不写进 <head>；页内 <link> 引用它也没有标准约定。
  • 页脚放一个人可见的链接，价值仅在于人和普通爬虫能发现它。
真正要紧的是三件事：① 根路径可匿名 GET（无登录、无反爬墙）；② 纯 Markdown 低噪内容；③ URL 长期稳定不搬家。再叠一层诚实边界：截至 2026 年，Anthropic / OpenAI 均未正式确认其 API 工具消费第三方 llms.txt，Google 明确忽略——它是零成本投机，不是必答题；真正必答的是 P0（正文事实静态可取）。

四条实验结论

  • ① P0 是唯一断点，且比预想更顽固。主线上模型两连空（文档页 + 主页），最终手里没有任何正文事实。值得注意的是 S2/S3 的细节：fetch 工具自带 JS 渲染（所以拿到了 JS 动态设置的文档 title），但正文是「再发一个异步 API 拉取」的——渲染等待期内没等到，照样空。「加载中」三个字就是铁证。对站点方的含义：SPA 异步正文对渲染型抓取器也是赌运气，SSR/SSG 直出才是确定性的。
  • ② 修站顺序倒挂实锤。hiascend 把 P3（llms.txt + robots LLM-Policy 行）、P1 的镜像半壁（llms-content 全量 MD 镜像）、P2（sitemap 全收录）都做了——投机项全做了，必答题（P0 正文静态可取）没答。图 A 价值条说「九成价值在 P0+P1，P0 独占大头」，实验里缺的恰是独占大头的那块。
  • ③ llms.txt 巨型化反例。llms.txt 12MB / 26,166 行，远超 llmstxt.org「每页一行链接 + 一句话简介」的精简索引初衷——这实际是把 llms-full.txt 的体量塞进了 llms.txt。后果有二：一次 fetch 预算读不完（等于不可用）；且近 2 万条收录里漏了「Ascend C 简介」这种最核心的入门文档——大而全 ≠ 覆盖关键。该做的是：llms.txt 收口到几百行以内的人工精选，全文放 llms-full.txt。
  • ④ MD 镜像的定位被精确验证。它正是本实验唯一走通的官方正文路径（S6）——「HTML 失败时的备用路径」名副其实。但触发它依赖「模型知道并去消费 llms.txt / 镜像」，而主流厂商未确认消费 llms.txt（理论 tab 图 D 的诚实边界），所以这个救场不保证发生；若 P0 修好，这些旁路全部自动变成锦上添花。优先级判断（P1 而非 P0）经受住了实测。

对本页理论 tab 的两处修正（实测驱动）

  • 修正 1 · llms.txt 的发现方式：图 D 及备答原说「AI 不通过 robots 发现 llms.txt，robots 里没有任何指令指向它」——这是 llmstxt.org 标准约定，但 hiascend 实测在 robots.txt 里写了 LLM-Policy: 行主动挂钩（超出标准约定的站点侧增强）。准确表述：「约定不依赖 robots 引路；站点可选挂 LLM-Policy 行——hiascend 已挂，是否被消费未知」。
  • 修正 2 · MD 镜像的「多数站不提供」：hiascend 实际提供了 llms-content/ 全量 MD 镜像（每条 llms.txt 详情链接都真实可访问、带 frontmatter）——这点上它走在多数站点前面。但 P0 未修使这些镜像的价值打折：它们只能救场，不能顶替正文直出。
诚实边界：① S4–S6 是 curl 传输层观测，用于还原 web_fetch 背后发生的传输事件，不是模型主动 fetch 序列的一部分——模型主线止于 S3；② 单次实验、单一模型（GLM）+ 单一工具链，不同厂商工具（是否渲染、渲染等待时长、是否消费 llms.txt）路径可能不同——S3 的「加载中」就是等待时长的直接证据；③ llms.txt 覆盖性 grep 基于当日快照（12MB 文件本身也可能变化）；④ 实验日期 2026-09-03，站点行为可能随版本迭代改变。
