# DACM · CHI 访谈实际提纲

> 版本：v0.1  
> 适用对象：有 AI Coding 使用经验的开发者  
> 单人时长：真实项目回放 35–45 分钟 + 两个情境推演各 20 分钟 + 回放访谈 15–20 分钟  
> 研究目的：理解开发者如何与 Agent、技术社区与本机现场协同推进开发任务；不评价参与者的技术能力，也不评价某个 AI 工具的高低。

---

## 使用说明

本提纲分为两部分：

- **A. 真实项目回放访谈**是 CHI 研究的主证据。请参与者回忆并尽可能回放一段近期真实任务。
- **B. 情境推演后的回放访谈**用于解释同一算子开发知识条件下，参与者为何信任、接管、换资料来源或提出验证需求。

标记说明：

- **[必问]** 每位参与者均需问到。
- **[追问]** 仅当参与者提及对应事件或回答不具体时使用。
- **[记录]** 访谈员应记录到协同轨迹表，不需逐字追问。

访谈原则：始终回到具体事件。遇到“AI 帮了我”“后来我自己解决了”“我不信它”这类概括性回答，继续问：**当时先发生了什么？你看到了什么？下一步是谁发起？为什么换人、换资料或停止？**

## 0. 开场与知情同意（5 分钟）

### 访谈员话术

> 感谢你参加。我们研究的是开发者和 AI 如何一起推进任务，以及文档、官网、社区在这个过程中怎样被使用。我们不考察你的技术水平，也没有标准答案。今天会先聊一段你真实使用 AI 的开发经历，再做两段简短的算子开发情境推演。你可以跳过任何问题，也不需要展示私有代码、账号、密钥或敏感项目内容。

> 如果你同意，我们会录音；你也可以选择性展示或口述 Agent 对话、终端片段、代码 diff、PR/Issue 或访问过的文档。研究材料会匿名处理，任何不希望保留的片段都可以在结束时标记删除。

### [必问] 确认

1. 你是否同意录音？
2. 你是否同意我们记录你自愿展示的屏幕、Agent 对话、终端片段或文档访问？
3. 是否有明确不能记录或引用的内容类型？

### [记录] 背景卡

- 参与者编号：
- 工作角色 / 年限：
- 常用语言、框架与开发领域：
- AI Coding 工具及使用频率：
- PyTorch / CUDA / CANN / Ascend 经验（无 / 了解 / 实际使用）：
- 是否曾用 AI 完成过从“需求到可运行结果”的完整任务：

## A. 真实项目回放访谈（35–45 分钟）

### A1. 选择一段真实任务（5 分钟）

#### [必问]

1. 请选最近一次你借助 AI 完成、且中间确实出现过卡点、判断或返工的开发任务。它是什么？
2. 当时你想达成什么结果？做到什么状态才算完成？
3. 这项任务发生在什么技术和项目背景下？包括语言/框架、版本、环境、数据或项目约束。
4. 你当时为什么决定让 AI 参与？原本不用 AI 会怎样做？

#### [追问]

- 这是真实工作、个人项目、学习任务，还是临时代码验证？
- 当时有没有时间压力、上线风险、性能/安全要求？
- 为什么选这个 AI 工具，而不是另一个？

#### [记录]

- 任务类型：检索 / 新功能开发 / 代码修改 / 调试 / 迁移 / 配置 / 其他
- 成功定义：功能 / 测试 / 性能 / 精度 / 代码评审 / 交付 / 其他
- 可回放材料：对话 / 屏幕 / 终端 / diff / PR / Issue / 文档 URL / 口述

### A2. 按时间回放协同过程（12–15 分钟）

#### [必问]

> 如果方便，请打开当时的 Agent 对话、终端、代码 diff、PR/Issue 或文档记录；如果没有材料，也请按时间顺序讲。

1. 请从任务开始讲起：第一步做了什么？之后发生了什么？
2. 哪些关键步骤是 AI 发起或主导的？哪些是你发起或决定的？
3. AI 在每一步扮演什么角色：检索者、解释者、方案起草者、代码生成者、排错者、审阅者，还是其他？
4. 任务中有没有回退、换问法、换模型、换资料来源、重做或暂停的时刻？请选一个最关键的时刻展开讲。

#### [追问]

- AI 的第一条建议是什么？你为什么采纳、修改或忽略？
- 当时你是先问 AI、先看代码、先查官网，还是先运行？为什么？
- 哪一步最耗时？哪一步最顺？
- 有没有 AI 看起来已经完成，但你后来发现还不能继续的时刻？

#### [记录：协同轨迹事件]

每个关键节点记录一行：

| 时间/顺序 | 主体 | 动作 | 使用/产生的证据 | 下一个主体 | 结果 |
|---|---|---|---|---|---|
| 例：T3 | Agent | 起草命令 | 官方示例 + 假设版本 | 开发者 | 开发者要求补版本 |

主体可选：开发者、Agent、官方知识、第三方社区、本机/项目环境。  
动作可选：检索、读取、起草、执行、决策、回灌、验证、回退。  
结果可选：推进、受阻、换源、接管、待核对、完成、放弃。

### A3. 知识从哪里来、如何被信任（8–10 分钟）

#### [必问]

1. AI 的关键建议来自哪里？官方文档、代码仓、社区帖子、搜索摘要、模型记忆，还是你提供的材料？
2. 你是否打开或核对过 AI 引用的来源？什么使你相信或怀疑它？
3. 是否发生过“页面存在但 AI 读不全/看不到”，或“AI 找到资料但资料不足以行动”？请举一个具体例子。
4. 版本、前置条件、可运行示例、错误处理或社区案例中，哪类信息最常缺失？

#### [追问]

- 你去官网/社区，是为了自己读，还是为了给 AI 找一段能用的证据？
- AI 是否明确区分“我有证据”“我在猜”“需要你补充”？
- 你是否更信官方、社区、代码仓，还是自己运行出来的结果？为什么？

#### [记录]

- 关键知识来源及用途：
- AI 是否给出可访问来源：是 / 否 / 不确定
- 参与者是否核验：是 / 否；原因：
- 知识状态：可得 / 受阻 / 不完整 / 版本不明 / 互相冲突 / 已验证

### A4. 人为何接管、如何回灌现场事实（8–10 分钟）

#### [必问]

1. 在哪个具体时刻你决定自己接手，而不是继续让 AI 尝试？为什么？
2. 你当时补给 AI 的是什么：环境信息、版本、报错原文、代码上下文、数据、业务目标还是判断标准？
3. 哪些关键判断你认为 AI 可以辅助但不应替你决定？为什么？
4. 报错、日志、运行结果如何回到 AI？什么信息在回灌中丢失或被重新解释？

#### [追问]

- AI 是否要求你提供这些现场信息，还是你主动意识到要补？
- 有没有信息只在你的本机/项目/业务场景里，公开资料永远找不到？
- AI 的建议让你增加了还是减少了核对工作？

#### [记录]

- 人工接管触发因素：证据不足 / 版本不明 / 本机事实 / 业务判断 / AI 错误 / 成本/时间 / 其他
- 回灌信息类型：版本 / 环境 / 日志 / 代码 / 输入输出 / 数据 / 约束
- 是否形成验证 checkpoint：是 / 否；内容：

### A5. 结果、责任与社区角色（5 分钟）

#### [必问]

1. 最终任务如何完成、暂时绕过或放弃？谁对结果负责？
2. 在这段任务中，你把官网、文档、论坛或样例当作“自己阅读的页面”，还是更像给 AI 找证据的地方？
3. AI 参与后，你访问技术社区的频率、方式或关注的信息变了吗？
4. 如果社区要同时服务开发者和 Agent，最先应该补什么？

#### [追问]

- 你希望社区让 AI 知道什么：可读正文、版本关系、可跑样例、错误案例、结构化接口、验证方式，还是其他？
- 是否存在只能由人/社区经验传递、不能只靠 Agent 汇总的知识？

## B. 统一算子开发情境推演后的回放访谈（每个情境后 5 分钟；最后合计 15–20 分钟）

> 情境 A 为“首个 AddCustom 算子跑通，知识链连续”；情境 B 为“动态 shape/Tiling 或 PyTorch 接入，知识需拼接”。不要求参与者有算卡，也不要求实际运行。

### B1. 单个情境完成后

#### [必问]

1. 请回看你刚才与 Agent 的过程：第一步为何这样问？
2. 你认为 Agent 的计划中哪部分已经足够具体，哪部分仍只是“看起来合理”？
3. 在真正进入 Ascend 环境前，你还必须获得或核对什么事实？
4. 你最终采用、修改或拒绝了 Agent 的哪条建议？为什么？

#### [记录]

- 情境：A / B
- 首次主体：开发者 / Agent / 材料
- 首次外部来源：官方 / 社区 / 搜索 / 无
- 是否主动要求现场事实：是 / 否
- 是否显式提出验证 checkpoint：是 / 否
- 最终计划：采纳 / 修改 / 拒绝 / 未形成

### B2. 两个情境的比较收束

#### [必问]

1. 两个情境中，哪个更容易让你把工作交给 AI？为什么？
2. 哪个情境中你更早开始自己接管、查资料或要求验证？为什么？
3. 当资料连续、可读且版本明确时，你与 AI 的分工发生了什么变化？
4. 当资料需要拼接、版本分散或关键内容难取得时，你希望 AI 和社区分别做什么？
5. 如果重新做一次，你希望 AI 在什么时刻主动停下、提问、给证据或要求你验证？

## C. 收尾与授权（3–5 分钟）

3. 是否同意匿名引用你的访谈原话或任务材料片段？

## 访谈员结束后：立即整理清单

1. 在 24 小时内补全协同轨迹表，不要只保留摘要。
2. 标出 3–5 个关键转折点：最早断裂、首次人工接管、关键回灌、验证 checkpoint、结果。
3. 记录参与者对社区角色的原话，并区分“真实项目经验”与“情境推演判断”。
4. 删除或脱敏参与者标记的敏感片段。
5. 不把情境推演的计划质量解释为真实 Ascend 上卡成功率或性能结果。
