# CHI 论文版 · 研究与写作简报

## 暂定题目

**谁在使用开发者社区？Agentic Coding 中开发者—Agent 协同轨迹与知识基础设施的角色转变**

英文工作题：*Who Uses Developer Communities? Collaboration Trajectories between Developers and Agents in Agentic Coding*

## 一句话主张

在 Agentic Coding 中，技术社区的实际使用单元从单一开发者转为“开发者—Agent 协同体”；不同的知识供给条件不会只改变 AI 的答案质量，也会重塑开发者在任务中的检索、审阅、接管、现场核对和责任承担。

## 论文的中心贡献

1. 以真实开发者的协同过程，识别 Agentic Coding 中开发者角色从“知识检索者”转向“目标设定者、现场事实提供者和结果验证者”的具体方式与边界。
2. 提出 DACM 作为解释框架，并以多主体协同轨迹分析记录知识生态、Agent、开发者和本机现场之间的事件与交接。
3. 用两种知识供给情境下的对照任务，归纳协同模式、协同断裂和“高 AI 参与但高人工责任”的现象。
4. 提出面向开发者—Agent 协同体的社区/文档设计启示：证据可见性、版本/前置条件、现场事实回灌与验证 checkpoint。

## 建议研究设计

### Study 0：生态审计（已有前期材料）

- 26 个 CANN/CUDA 任务的 Agent 检索与取证记录。
- 用途：选择知识供给条件差异显著、用户目标相近的任务对；不是论文的主实验，也不用于生态排名。

### Study 1：真实项目回放访谈（主研究，必须补）

- 20 名有 AI Coding 使用经验的开发者；不要求拥有 Ascend 算卡或完成 CANN 项目。
- 每人选择一段近期使用 Agent 完成、且中间出现判断、返工、验证或资料查找的真实开发任务。
- 以可提供的材料为锚点回放：Agent 对话、代码 diff、终端片段、Issue/PR、文档访问记录或屏幕；不要求提交完整私有代码。
- 采集：访谈录音、经同意的任务材料和研究者共同绘制的协同轨迹；重点记录知识来源、主导权迁移、现场事实、人工接管及验证方式。
- 分析：反思性主题分析 + 多主体协同轨迹编码；以概念饱和而非统计显著性决定解释边界。

### Study 2：统一算子开发情境推演（补充对照，必须补）

- 为所有参与者提供同一份算子开发情境包：任务目标、starter code、CANN/torch_npu 版本信息、文档/社区材料入口及一段编译或运行日志。
- 参与者可使用指定 Agent、浏览器与终端/文本材料，提出下一步实施与验证计划；不要求真实上卡编译或运行。
- 情境包分两种知识条件：一类提供连续、可读且版本较明确的资料；另一类呈现跨资料拼接、版本分散或关键正文不可取得的条件。采用 AB/BA 顺序平衡。
- 采集 Agent 对话、资料访问、过程性选择和书面实施/验证计划，并进行简短回放追问。

该设计不测量真实 Ascend 算子端到端完成率、性能或环境安装难度；它测量开发者在任务尚未能直接执行时，如何与 Agent 共同使用知识、识别未知、提出现场信息需求并设计验证。

## 研究问题

- RQ1：开发者在 Agentic Coding 中如何在检索、起草、执行、核对与验证之间重新分配工作？
- RQ2：不同知识供给条件如何塑造开发者与 Agent 的协同轨迹及角色迁移？
- RQ3：开发者如何识别、修复或承担 Agent 无法取得知识和无法取得现场事实所造成的协同断裂？
- RQ4：技术社区应如何面向开发者—Agent 协同体重新组织知识与交接？

## 建议章节

1. 引言：开发者社区的用户发生了什么变化？
2. 相关工作：AI 辅助编程、开发者知识实践、协同与基础设施。
3. 形成性生态审计：为什么选择这些对照任务与知识情境。
4. 方法：参与者、任务、过程数据、多主体协同轨迹分析。
5. 发现：协同模式、断裂和角色迁移。
6. DACM：从经验发现回到协同机制框架。
7. 设计启示与讨论：面向协同体的知识基础设施。
8. 局限与结论。

## 不应成为主结论的内容

- “CANN 比 CUDA 差多少”。
- 仅凭单 Agent 分数对开发者行为作因果推断。
- 未经真实开发者数据验证的 DAR 数值。
