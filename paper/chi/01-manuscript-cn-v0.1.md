# 谁在使用开发者社区？

## Agentic Coding 中开发者—Agent 协同轨迹与技术知识生态的角色转变

> 中文论文工作稿 v0.1（面向 CHI 的叙事版本）  
> 状态：引言、框架、研究设计与讨论初稿完成；参与者研究尚未实施，所有经验性发现均保留为待填证据位，不能作为投稿结论。  
> 研究对象：有 AI Coding 经验的开发者（目标约 20 人）；真实项目回放访谈 + 统一算子开发情境任务；以既有 CANN/CUDA 知识生态审计作为形成性研究。

---

## 摘要

AI Coding 正在改变开发者使用技术社区的方式。开发者不再只是在官网、文档和社区之间自行检索与拼接知识；他们还把任务交给能够检索、阅读、调用工具、修改代码并根据反馈重试的 Agent。由此，技术知识生态的使用单元不再是单一的“开发者”，而是由开发者、Agent、知识来源和本地工程环境构成的协同体。然而，现有研究往往分别讨论代码生成工具的输出质量、开发者对建议的采纳，或开发者门户的传统可用性，较少解释 Agent 的运行方式如何与开发者的现场判断、知识环境和验证活动共同塑造任务推进。

本文提出开发者—Agent 协同机制（Developer–Agent Collaboration Mechanism，DACM），将 Agentic Coding 描述为一个由任务设定、上下文建构、证据取得、候选行动、工具执行、现场验证和结果回灌构成的循环。DACM 不将 Agent 视为一次性回答机器，也不将开发者视为被替代的执行者；它关注两者如何在不同任务阶段转移主导权，以及技术知识生态如何影响这种转移。我们首先对 CANN 与 CUDA 的 26 个开发任务进行形成性知识生态审计，用于识别“结果目标相近、但知识供给条件显著不同”的任务情境。随后计划开展约 20 名开发者的两部分质性研究：真实项目回放访谈，以及使用个人 IDE/CLI/Agent 完成统一连续工程情境的任务观察。我们收集对话、屏幕、终端、资料访问、代码差异和回放访谈，并以多主体协同轨迹分析编码检索、事实补充、建议采纳、人工接管、验证 checkpoint 和停止点。

本文预期贡献为：（1）以 Agent 的典型运行循环为基础，提出解释开发者—Agent 协同的 DACM；（2）提出多主体协同轨迹分析，使知识来源、Agent 行动、人类接管和本地环境反馈成为可追溯过程数据；（3）说明技术社区如何从“供人阅读的内容集合”转变为支撑人机协同的知识基础设施；（4）给出面向社区、文档与 Agent 工作流的设计启示。本文将形成性审计和参与者研究清晰区分：前者用于构造知识条件与研究材料，后者才用于支持关于开发者行为的经验性结论。

**关键词：** 人机协同；AI Coding；Coding Agent；开发者体验；技术社区；开发者文档；质性研究

## 1. 引言

当开发者遇到一个陌生 API、编译错误、版本冲突或性能问题时，过去的典型路径是：搜索关键词、打开官方文档、比较社区答案、阅读代码、在本机运行，再据此调整下一步。AI Coding 工具正在重新组织这条路径。开发者可以给出目标或报错，Agent 会检索资料、读入工程文件、生成补丁、调用终端、观察结果并继续修改。开发者仍然需要决定目标、提供权限和现场信息、辨别证据、确认风险，并对最终交付负责；但他们不必在每一轮都亲自执行检索和起草。

这不是简单的“人做得更少、AI 做得更多”。Coding Agent 的行动能力来自一个具有边界的循环：它基于当前上下文提出假设，通过搜索、文件读取或工具调用取得外部证据，生成或修改候选方案，再等待工具反馈或开发者补充事实。它通常无法直接知道本机版本组合、硬件拓扑、私有代码语义、业务约束和验收标准；在证据不足或工具受阻时，也可能以不完整线索继续推断。因此，一个表面上由 Agent 主导的阶段，仍可能要求开发者承担大量的核对与接管工作。

这一变化使技术社区的角色发生转变。官方文档、示例、版本矩阵、Issue、论坛帖子和搜索入口仍服务于人类开发者，同时也成为 Agent 获取证据、校验假设和组织行动的知识基础设施。页面对人类可见，不代表 Agent 能稳定取得正文；Agent 能生成流畅代码，也不代表代码所依赖的版本、环境和验证条件已被锁定。若研究只测量最终答案是否“看起来正确”，便难以判断问题来自模型、检索链路、文档工程、版本治理、社区供给，还是缺失的现场事实。若只考察传统门户导航与页面体验，又无法解释为什么开发者在 Agent 给出方案后仍反复查找、回灌和验证。

本文研究的问题是：**在 Agentic Coding 中，开发者、Agent、技术知识生态和本地工程环境如何共同推进开发任务？** 我们提出 DACM，用以描述和分析协同中的角色、行动、证据状态与交接。框架吸收了对 Coding Agent 工作模式的理解，但其重点不是比较模型或揭示模型内部参数机制；重点是解释 Agent 的检索—推理—行动—反馈循环如何进入真实开发过程，并如何改变开发者与技术社区的关系。

本研究采用顺序式、混合证据的设计。Study 0 是一项形成性生态审计：在 CANN 与 CUDA 的 26 个结果目标相近的开发任务上，以统一协议观察一个具备实时检索和网页读取能力的 Agent 如何获取、判断与组织技术知识。它不被用作“谁更强”的主结论，而被用来选择资料连续性、版本明确度和可获取性存在差异的任务情境。Study 1 是开发者近期 AI 协同项目的回放访谈；Study 2 是围绕统一 AddCustom → PyTorch 连续工程的情境任务与任务后回放。参与者使用自己的 IDE、CLI 和常用 Agent；研究不要求提供昇腾算卡，也不以真实上卡完成率或性能为结果变量。

本文作出以下贡献：

1. 提出 DACM，说明 Agent 的上下文建构、检索、工具行动与反馈循环，如何同开发者的目标设定、现场事实提供、判断与验证相互耦合。
2. 提出多主体协同轨迹分析，将一次开发任务表示为开发者、Agent、官方/第三方知识来源与本机环境之间的有序事件，而非仅记录最终答案或满意度。
3. 给出一项以知识生态审计支撑质性任务设计的研究方案，区分“知识无法被 Agent 获得”和“知识可得但必须由人提供现场事实”两类协同断裂。
4. 提出面向技术社区的设计空间：可行动的证据单元、版本与前置条件的显式化、可回灌的现场事实接口，以及验证 checkpoint。

## 2. 相关工作

### 2.1 AI 辅助编程中的采纳、监督与协作

既有研究表明，代码补全和生成式 AI 会改变开发者的写作、审阅、学习、信任和责任分配。开发者会将 AI 建议当作草稿、对话伙伴、搜索替代或快速试验工具，而非稳定的自动编程代理；他们也会通过阅读 diff、运行测试、比较外部资料和限制 Agent 权限来管理风险 [待补：Barke et al.; Vaithilingam et al.; Bird et al.; Denny et al.]。这些工作有力说明“是否采纳”不是二元决定，但较少将 Agent 所依赖的外部技术知识及其可获得性作为协作机制的一部分。

本文沿用人类监督与协同的视角，但把分析单位从“模型输出—开发者反应”扩展为“任务推进中的多主体事件”。我们特别关注：开发者何时将任务交给 Agent，Agent 何时需要外部知识或现场事实，何时由开发者接管，以及验证如何改变下一轮行动。

### 2.2 Coding Agent 的工作循环与外部边界

与只在编辑器中预测下一段代码的模型不同，Coding Agent 往往以循环方式工作：理解目标和现有上下文，规划或选择下一步，检索网页或项目文件，调用编辑、终端、测试等工具，解释反馈并继续迭代 [待补：ReAct；tool-use / SWE-agent / OpenHands 等研究]。这种循环使 Agent 能够把静态知识转为候选行动，但也带来几个不可消除的边界。

第一，Agent 的行动取决于可见上下文；未被提供或无法通过工具获得的版本、配置、私有逻辑和业务标准，不能被可靠推断。第二，检索到来源不等于获得足够证据：页面正文、示例、版本范围与失败处理是否可得，会影响后续建议。第三，工具输出本身是协同的一部分：编译日志、测试失败、运行时状态和人工观察必须被解释、筛选并回灌。因而，本文不尝试以黑箱“模型能力”解释全部结果，而以 Agent 的可观察运行循环作为研究设计与编码的理论基础。

### 2.3 开发者知识实践、文档与技术社区

开发者通过文档、示例、搜索、问答社区和同行网络获取并验证知识。相关研究长期指出，API 文档的可发现性、示例质量、版本更新、错误说明与社区经验会影响学习、集成和排障 [待补：开发者文档、信息觅食、开发者社区与 API 可用性文献]。传统开发者体验研究通常围绕人类访问者的旅程、触点和认知负担展开。

本文提出，当 Agent 参与其中时，技术社区同时承担四种作用：**证据源、行动脚手架、冲突校验器和协同记忆**。这意味着“文档可用性”还需要考虑 Agent 是否能发现、读取、引用和将其转化为带前置条件的行动。我们不把这一转变称为“AI 替代开发者”，而称为技术知识生态面向开发者—Agent 协同体的重新组织。

### 2.4 本研究的定位

本文位于 HCI、人机协同与开发者工具研究的交叉处。它不主张一个新的模型架构，也不以 CANN/CUDA 的性能比较为目标；它研究在具备检索和工具调用能力的 Agent 条件下，技术知识供给如何改变开发者的协同动作和责任。与单纯的 Agent 基准不同，本文把本地环境和开发者判断纳入过程；与单纯的开发者体验审计不同，本文明确分析知识如何进入 Agent 的行动循环。

## 3. DACM：开发者—Agent 协同机制

### 3.1 四类参与者与一个循环

DACM 将协同开发表示为四类参与者构成的闭环（图 1）：

```text
技术知识生态 ──证据、样例、版本、讨论──→ Agent
     ↑                                        │
     │                                        │ 候选行动、解释、补问
     │                                        ↓
开发者 ←── 目标、判断、授权、责任 ────→ 本地工程环境
     ↑                                        │
     └──────── 观察、日志、结果、约束 ────────┘
```

- **开发者**：设定目标与边界，选择是否授权，提供任务语义和现场事实，评估风险并对结果负责。
- **Agent**：建构上下文，检索和读取知识，形成候选计划或代码，调用可用工具，解释反馈并发起下一轮行动。
- **技术知识生态**：提供官方文档、样例、版本信息、代码仓、社区讨论和搜索入口；它决定证据的可发现、可读、可引用与可验证程度。
- **本地工程环境**：包含代码、依赖、硬件、配置、数据、终端输出与测试结果，是最终约束和验证发生的地方。

一个循环不是固定的线性流程。开发者可能先给出报错再请求 Agent 解释；Agent 可能先读仓库再搜索；工具失败后，人可能直接接管而不再让 Agent 重试。DACM 因此将循环理解为可回退、可中断、可重新分配主导权的协同机制。

### 3.2 从 Agent 运行模式推导分析维度

为避免框架只是一组抽象角色，我们从可观察的 Agent 工作模式推导五类分析维度：

| 维度 | Agent 的典型活动 | 开发者不可替代的活动 | 可观察证据 |
| --- | --- | --- | --- |
| 目标与上下文 | 读取任务、代码和已有对话；提出澄清问题 | 设定优先级、披露约束、判断哪些上下文可共享 | 初始提示、补充事实、权限选择 |
| 知识取得 | 搜索、读文档、检索仓库、比较来源 | 判断来源是否适用于当前项目 | 查询词、URL、打开/放弃的页面 |
| 候选行动 | 起草代码、命令、修改计划或诊断假设 | 决定是否采纳、限制影响范围 | Agent 输出、diff、采纳/拒绝 |
| 现场执行 | 调用终端、测试或其他工具（若获授权） | 提供环境状态，处理不可授权或高风险动作 | 命令、日志、测试与运行状态 |
| 验证与回灌 | 基于反馈修订假设或继续检索 | 判断结果是否满足业务/质量要求 | checkpoint、回灌内容、停止原因 |

这些维度是 Study 1 和 Study 2 的观察与编码依据。它们不是声称每个 Agent 都以同样算法运行，而是描述在用户可见层面足以影响协同体验的行动模式。

### 3.3 协同事件与交接

DACM 的最小分析单位是**协同事件**。每个事件记录：

`时间 / 发起者 / 动作 / 输入证据 / 输出或状态 / 主导权变化 / 下一步去向`。

例如，“Agent 读取编译日志后建议升级插件”并不是完整的协同结果；研究还会记录建议引用了什么证据、开发者是否提供了版本表、是否执行、失败后如何回灌、谁决定停止。我们将特别识别以下交接事件：

- **事实请求**：Agent 明确需要本地版本、日志、配置、数据或验收标准；
- **证据切换**：开发者或 Agent 从官方文档切换到样例、社区、代码或本机环境；
- **人工接管**：开发者因证据不足、风险、效率或信任原因亲自检索、修改或决策；
- **验证 checkpoint**：参与者以测试、编译、代码审查、版本核对或业务判断确认一项候选行动；
- **停止点**：任务达到可接受状态、被暂时搁置，或因不可获得信息而无法继续。

### 3.4 协同有效性的工作性定义

本文不以“Agent 做了多少工作”度量有效性。一个协同片段在以下条件下被视为更有效：它以可追溯证据推进了任务；明确了尚缺的现场事实；减少了无效重复与不可解释的风险；并形成与任务风险相称的验证闭环。相反，表面上节省输入时间、却迫使开发者反复核对幻觉或重新拼接来源的过程，不应被计为有效协同。

因此，本研究将有效性拆为四个过程性结果：

1. **推进性**：是否使任务进入下一可行动状态；
2. **证据充分性**：建议能否追溯到适用的资料或现场事实；
3. **交接清晰度**：Agent 与开发者是否明确谁需要补充什么、为什么；
4. **验证可达性**：是否存在参与者能够实际执行或判断的 checkpoint。

这些不是预设的量表分数，而是用于跨案例比较的分析维度。后续可在数据充分后形成编码频次、序列模式与参与者叙述的三角验证。

## 4. 形成性研究：技术知识生态审计（Study 0）

### 4.1 目的与边界

Study 0 的目的不是声称“CANN 与 CUDA 哪个更好”，而是为参与者研究提供有依据的任务情境。我们需要知道：哪些任务拥有连续、可读且版本明确的资料；哪些任务要求跨文档拼接；哪些场景中 Agent 可能被页面可访问性、深层知识或版本关系卡住。只有先识别这些条件，Study 2 才能避免把“不同任务难度”误认为“知识条件差异”。

### 4.2 任务与协议

审计覆盖 26 个开发结果目标，包括环境与安装、算子开发、训练、推理部署、性能优化、调试和迁移。每个目标在 CANN 和 CUDA 中使用各自真实术语构造问题对；固定一个具有实时检索与网页读取能力的 Agent，记录搜索、正文读取、来源切换、版本证据、第三方支撑、检索成本与最终回答的可执行条件。

审计使用 11 项指标描述官方与第三方知识、模型先验、检索成本和答案产出。它还使用开发者门户生命周期审计记录人类直接进入该生态的触点条件。两套指标不被合并成单一分数：前者描述 Agent 对任务知识的可用性，后者描述开发者基础体验。

### 4.3 形成性产出

审计已有三类形成性产出，供 Study 2 取材而非直接支撑行为结论：

- **任务条件卡**：为每个候选节点标明目标、资料入口、版本线索、预计的现场事实需求与风险；
- **连续工程情境包**：AddCustom → PyTorch 的五个节点，分别是 D 写 Kernel、M Tiling、X 编译/内存、O 注册接入、L 精度验收；
- **知识条件样本**：连续可读且版本较明确的资料链，与跨资料拼接、版本分散或关键内容难以直接获得的资料链。

这里的“知识条件”不是为了诱导参与者失败，也不是假装有可用算卡。它使研究者能够观察：在不能或不需要真实上卡的情况下，参与者如何利用 Agent、资料和已有工程证据提出下一步、发现未知并设计验证。

## 5. 研究方法：开发者协同轨迹研究

### 5.1 总体设计

我们采用两部分、同一参与者的质性研究。Study 1 先获得参与者在真实工作中的协同实践；Study 2 再以共同的、可控的工程情境观察知识供给如何影响过程。这样的顺序避免把情境包中的行为当作日常习惯，也避免仅凭回忆而缺少可比较的过程证据。

| 部分 | 活动 | 目标 | 预计时长 |
| --- | --- | --- | ---: |
| 开场 | 研究说明与背景问卷 | 确认经验、工具和记录边界 | 10 分钟 |
| Study 1 | 真实项目回放访谈 | 重建一次近期协同任务的轨迹 | 35–45 分钟 |
| Study 2 | 连续工程情境任务 | 观察知识条件下的协同动作 | 50–60 分钟 |
| 回放 | 任务后访谈与短量表 | 解释接管、验证与信任变化 | 15–20 分钟 |
| 收束 | 确认可引用范围 | 处理删改、匿名与后续联系 | 5 分钟 |

### 5.2 参与者与招募

目标招募约 20 名具有 AI Coding 使用经验的开发者。样本追求角色、年限、常用 IDE/CLI、使用的 Agent 类型和任务领域的最大差异，而非统计代表性。纳入条件为：（1）近三个月内在实际开发中使用过具备对话、代码生成、检索或工具调用能力的 AI 工具；（2）愿意回放一段含有判断、资料查询、返工或验证的开发任务；（3）可以在自己的设备上使用习惯的 IDE/CLI/Agent 完成 Study 2。参与者无需拥有昇腾设备、CANN 环境或完整私有项目代码。

研究者应记录招募渠道、补偿、职业身份、开发年限与 AI 工具经验，并在伦理审批或知情同意材料中明确屏幕、终端、对话和代码 diff 的采集范围。私有代码、密钥、客户信息与可识别项目名称不应被要求提供；参与者可随时跳过、遮盖或删除片段。

### 5.3 Study 1：真实项目回放访谈

参与者选择一段近期使用 Agent 的开发任务，优先选择中间出现过查资料、环境差异、返工、验证或责任判断的案例。访谈不要求把完整私有工程交给研究者；可使用 Agent 对话、终端片段、提交 diff、Issue/PR、文档访问记录、截图或参与者口述作为回放锚点。

主持人按照时间追问：任务目标是什么；最初提供给 Agent 的上下文是什么；Agent 做了哪些检索或代码行动；哪些资料被信任或放弃；何时需要参与者补充事实；何时开始验证；是否出现人工接管、回退或停止。主持人不要求参与者“制定计划作业”，而是在其真实叙事中定位已经发生的目标设定、事实补充、证据选择和判断。

### 5.4 Study 2：统一连续工程情境任务

Study 2 向参与者提供一个可下载的轻量工程情境包，而不是模拟一个功能有限的 IDE。参与者在自己熟悉的 IDE、CLI、浏览器和常用 Agent 中工作；工程包提供 starter code、环境清单、阶段性资料、代码片段和预先记录的日志/输出。参与者无需在本地安装 CANN 或获得算卡资源。

任务不是“修复五个报错”，而是沿一个完整算子工程推进：

1. **D：写 Kernel**——理解 AddCustom 工程骨架与设备/dtype/format 约束；
2. **M：Tiling**——处理动态 shape、分块、尾块与 Tiling 信息；
3. **X：编译/内存**——阅读编译、launch 或内存相关证据，判断下一步；
4. **O：注册接入**——处理框架绑定、版本线索与测试输出；
5. **L：精度验收**——解释参考结果、阈值与尚需验证的边界。

每一节点都允许参与者自然地搜索、询问 Agent、修改文本或代码、运行本地安全脚本、记录不确定性，或说明在真实环境中希望验证什么。研究者只提醒时间和记录边界，不解释答案、不替参与者操作，也不预告根因。资料以两种知识供给构型呈现，顺序做 AB/BA 平衡：一类资料形成较连续、可读且版本明确的证据链；另一类要求在多份资料之间拼接，或留有版本/正文/现场事实缺口。具体材料在正式研究前须经 pilot 校准，确保两种构型的区别不等同于文本数量或任务难度。

### 5.5 数据采集

在取得同意后，采集以下材料：

- 访谈音频与必要的屏幕录像；
- 参与者与 Agent 的对话片段；
- 终端命令和输出、资料 URL、文件/代码 diff；
- 研究者的事件时间线与观察笔记；
- 任务后回放访谈；
- 对证据清晰度、控制感、验证可行性和继续使用意愿的简短自评（仅作解释性材料，不做大样本显著性推断）。

每一位参与者使用匿名编号。原始记录、去标识转录稿、事件表与可引用片段分别存放并设置访问权限。任何可公开的引文都须再次经参与者确认。

### 5.6 分析：多主体协同轨迹分析与主题分析

分析由两个互补层组成。

第一层是**多主体协同轨迹分析**。研究者从转录、屏幕与操作记录中切分事件，并使用下表的初始码本；两名研究者先对若干样本共同编码、讨论歧义、修订定义，再独立编码其余材料并持续比较。编码一致性用于发现定义问题，不以单一系数取代质性解释。

| 码类 | 初始代码 | 判定问题 |
| --- | --- | --- |
| 发起与上下文 | 目标设定、上下文补充、权限/边界 | 谁定义问题与可行动范围？ |
| 知识取得 | 官方资料、第三方资料、项目内资料、模型先验、来源切换 | Agent/人从哪里获取证据？ |
| 协同行动 | 生成、检索、编辑、执行、解释、追问 | 谁主导下一步？ |
| 断裂与接管 | 证据不足、版本不明、现场事实缺失、风险顾虑、人工接管 | 为什么协同没有继续自动推进？ |
| 验证与收束 | 测试、日志核对、代码审查、业务判断、回退、停止 | 什么构成可信的结束？ |

第二层是反思性主题分析。研究团队在跨案例比较中归纳协同模式，例如“Agent 作为快速起草者”“以现场事实为中心的回灌循环”“以证据追溯为中心的审阅”“因版本不确定而发生的人工拼接”。这些主题必须由参与者叙述、轨迹事件和实际材料共同支撑，而不能由 Study 0 的生态评分直接推断。

### 5.7 研究质量与边界

我们将通过案例链、负例搜索、研究者备忘录、跨材料三角验证和参与者引文核对提高可信度。研究不试图测量模型的普适能力，也不将 20 名参与者的经验概括为所有开发者。Study 2 的价值是控制知识供给与任务骨架，并不等同于真实算卡上的端到端开发；真实世界的环境配置、团队协作和长期学习仍需要后续纵向研究。

## 6. 发现（待参与者研究完成后写入）

> 本节保留为论文结构与证据标准，当前不填入假设性结论。正式写作时，每个发现至少应包含：跨案例模式、2–4 个匿名引文、一个协同轨迹片段、反例或边界条件，以及与 Study 0 的关系说明。

### F1. 【待填】Agent 将“找资料”压缩为候选行动，但没有消除开发者的证据判断

**应回答的问题：** 参与者何时把 Agent 当作搜索替代、草稿生成器或解释器？他们如何判断来源、代码和命令是否适用？何种任务中 Agent 节省了检索成本，何种任务中反而增加了核对成本？

**拟放证据：** 一条从“目标→Agent 搜索/生成→人查证→采纳/修改”的轨迹；不同经验参与者的对照引文。

### F2. 【待填】现场事实不是 Agent 的“缺陷”，而是开发者在协同中提供的关键资源

**应回答的问题：** 哪些事实只能来自本机环境或业务现场？参与者如何识别并回灌版本、日志、依赖、数据和验收标准？哪些 Agent 追问被认为有帮助，哪些被认为只是把负担推回给人？

**拟放证据：** D/M/X/O/L 中至少两个节点的事实请求与验证 checkpoint 对照。

### F3. 【待填】知识供给条件改变的不是单次答案，而是协同轨迹的形状

**应回答的问题：** 连续且版本明确的资料链是否更容易产生短的“建议—验证”循环？跨资料拼接或版本不清的条件下，是否更多出现来源切换、人工接管、重复追问或停止？这一差异是否受参与者经验和工具偏好调节？

**拟放证据：** AB/BA 条件下的轨迹小倍图；至少一个负例，说明资料充分也仍可能因现场约束而需要人接管。

### F4. 【待填】开发者的角色转变为目标、边界、事实与责任的协调者，而非被动审批者

**应回答的问题：** 参与者如何描述自己“仍在做什么”？他们是否把验证、授权、风险判断、任务拆分和停止视为核心劳动？这种角色是否随任务风险与 Agent 能力改变？

**拟放证据：** 任务后回放中的角色叙述；一张阶段化的协同负荷图。

## 7. 从经验发现到 DACM 的呈现方式

正式论文中，DACM 不应在数据之前被写成完备的普遍理论。更合适的呈现是：Study 0 提供知识条件的形成性背景；Study 1 与 Study 2 的轨迹和主题揭示反复出现的协同机制；DACM 则是研究团队对这些机制的归纳。框架将回答三个问题：

1. **Agent 为什么在某些环节推进得快？** 因为目标、可读取证据和可调用工具形成了足够的行动闭环；
2. **为什么它在另一些环节需要人介入？** 因为缺少可获得知识、适用版本或不可外推的现场事实；
3. **技术社区如何介入这种协同？** 它决定了证据能否被发现、引用、行动化和交叉验证。

### 7.1 协同配比图：描述性汇总，而非替代率

我们保留“开发者—Agent 主动占比与核对负荷”的阶段图（图 4）作为一种**描述性总结图**。紫色与红色扇面表示在某一阶段中 Agent 与开发者主导事件的相对比例；圆面积表示阶段投入；金色外环表示必须回到本机或业务现场核对的负荷。它的用途不是宣称“AI 替代了 65% 的工作”，而是直观展示一个关键张力：Agent 主导比例高，不等于开发者的验证责任低。

可编辑的交互源图见：[开发者—Agent 协同配比模型](../research/assets/dacm-developer-agent-ratio-model.html)。

在正式投稿版本中，图中比例必须由预先定义的事件编码计算，并报告分母、阶段边界、编码规则与不确定性；在真实参与者数据完成前，该图仅为可视化原型，不能被作为经验结果。

## 8. 面向开发者—Agent 协同体的设计启示

### 8.1 将知识发布为可行动的证据单元

技术文档不应只按概念或产品目录组织，也应围绕任务给出 Agent 和人都能使用的证据单元：目标、适用版本、前置条件、最小命令/代码、预期输出、常见失败、恢复路径和出处。这样，Agent 能够引用而非拼凑，开发者也能够快速判断建议是否适用。

### 8.2 把版本关系从背景说明变成可查询的约束

版本、芯片、驱动、框架、插件和工具之间的配套关系，常常是协同最早需要补充的现场事实。社区应提供机器可读且可深链的兼容矩阵、版本选择器和最小环境 manifest；Agent 应在不确定时显式请求这些事实，而不是静默猜测。

### 8.3 为现场事实回灌设计接口

开发者并不总能将整个环境暴露给 Agent，但可以安全地提供经过脱敏的版本摘要、日志片段、依赖树、测试结果或错误码。工具应帮助用户选择、压缩和标注这些事实，并让 Agent 解释“为什么需要它”“它将影响哪个判断”。这能把模糊的“请提供更多信息”变成明确且可控的协同交接。

### 8.4 将验证 checkpoint 置于生成之后、自动执行之前

对于版本敏感、高风险或影响范围大的修改，好的体验不是让 Agent 一路自动执行，而是在关键节点展示证据、假设、影响范围和最小验证方式。开发者可据此选择批准、缩小操作范围、补充事实或接管。验证 checkpoint 同时是安全机制、学习机制和责任边界。

### 8.5 支持从协同过程回流到知识生态

反复出现的 Agent 补问、人工接管、版本冲突和无法验证的命令，都是知识基础设施的需求信号。若社区能以隐私保护的方式聚合这些协同断裂，就能将一次性问答转化为文档、样例、版本治理和社区支持的持续改进依据。

## 9. 讨论

本文的核心不是“用户从人变成 AI”。更准确地说，技术社区正在面对一种新的复合使用者：开发者与 Agent 共同进入、共同读取、共同组织并共同验证技术知识。开发者依然是责任主体，但其劳动更集中于目标和边界设定、现场事实提供、风险判断、验证与收束。Agent 则承担大量候选方案的检索、压缩、起草和局部行动。两者之间的关系取决于知识生态是否支持可靠证据流动。

这一视角也解释了为什么仅以模型正确率、满意度或完成时间不足以评价协同。模型正确率难以解释知识在哪里丢失；满意度可能忽略开发者为防止错误所承担的隐性核对；完成时间则会受到经验、任务陌生度、环境条件和工具熟练度的共同影响。DACM 关注的是这些结果背后的机制：谁在何时拥有什么证据，谁补充了什么事实，为什么发生交接，以及验证是否闭环。

对 HCI 而言，本文将 Agent 的运行模式视为一种设计材料，而不是遥远的算法细节。只有理解 Agent 的上下文、检索、工具行动和反馈边界，才能设计合理的交接、提示、资料与验证机制；但研究目标始终是开发者的协同体验及其知识基础设施，而不是提出一种更强的 Agent。

---

## 10. 局限与后续工作

本研究具有明确边界。首先，Study 0 固定一个 Agent 与其工具条件，不能代表全部模型、浏览器、企业检索系统或未来版本。其次，CANN/CUDA 审计服务于任务情境构造，不应被当作对技术生态整体能力或硬件竞争力的永久排名。第三，约 20 人的质性研究适合机制发现与理论生成，不适合估计总体比例或因果效应。第四，Study 2 不提供真实算卡环境，关注的是资料、Agent、工程证据和验证规划的协同；它不能替代真实上卡任务、长期项目或团队协作中的观察。

后续工作可在三方面扩展：（1）开展纵向现场研究，观察开发者如何随时间建立对 Agent 的信任与验证习惯；（2）在相同任务和知识生态上比较不同 Agent 的检索、工具权限和上下文策略；（3）将协同轨迹中的高频断裂转化为可 A/B 验证的文档与工具设计。

---

## 11. 结论

在 Agentic Coding 中，技术社区不再只是开发者查阅的页面集合，而是开发者—Agent 协同体共同依赖的知识基础设施。本文提出 DACM，以 Agent 的可观察工作循环为基础，分析目标、知识、行动、现场事实、交接和验证如何共同决定任务能否推进。通过形成性知识生态审计与计划中的开发者协同轨迹研究，本文将把“AI 是否有用”从单一答案质量问题，转化为可观察、可设计和可改进的人机协同机制问题。
