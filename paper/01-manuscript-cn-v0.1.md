## 摘要

生成式人工智能正成为开发者检索技术知识、起草代码、解释错误和完成部署任务的重要协作者。在 Agentic Coding 中，开发者不再独自搜索、阅读和拼接资料，而是通过提出目标、审阅建议、提供现场事实、执行验证和回灌结果，与 Agent 共同推进任务。由此，技术生态中的文档、样例、版本信息和社区内容不再仅服务于人类阅读，也构成 Agent 生成可执行建议的知识基础设施。然而，现有开发者体验研究主要考察人类用户界面与任务流，面向大语言模型的评估又通常停留在问答正确性，较少解释技术知识生态如何经由 AI 建议、人类验证与多次交接共同塑造开发任务。

本文提出**开发者—Agent 协同机制框架**（Developer–Agent Collaboration Mechanism Framework, DACM），并以 CANN 与 CUDA 为案例开展任务级分析。DACM 将协同开发理解为由“任务目标—知识取得—Agent 建议—人机交接—本机验证—反馈回灌”构成的多主体过程。研究以 26 个覆盖环境配置、算子开发、训练、推理部署、性能优化、调试和迁移的开发任务为观察单位，为两种生态设计结果目标一致的真实问题对。一个具备实时检索与网页读取能力的 AI Agent 按统一协议执行搜索、取证与作答；研究以官方知识、第三方知识和模型自带知识为三类来源，记录官方可发现性、可抓取性、正文详尽度、版本清晰度、第三方支撑、检索成本与答案可执行性等 11 项指标。同时，研究将检索日志、开发者门户触点与本机执行要求组织为多主体协同轨迹，以识别协同中的断裂、交接与人工验证负荷。

结果显示，知识生态的 AI 可用性具有显著任务相关性，而非单一站点属性：CANN 在安装、迁移和若干训练/优化任务中可提供较完整的机器可读知识支撑，但在自定义算子等深层专有任务中，核心操作正文的机器读取障碍、版本信息分散和第三方互证不足会叠加出现。基于任务日志与协同轨迹分析，本文进一步提出开发者—Agent 协同配比图（Developer–Agent Ratio, DAR），作为 DACM 的阶段化汇总表达：在每一个开发阶段同时表示 Agent 主导动作、开发者主导动作、阶段投入，以及不可替代的本机/业务事实核对负荷。DAR 不将 AI 使用比例等同于自动化程度，而强调高 AI 参与仍可能伴随高人工验证需求。

本文的贡献包括：（1）提出 DACM，说明技术知识生态、Agent 与开发者如何通过知识取得、交接和现场验证共同完成任务；（2）提出多主体协同轨迹分析，将检索、起草、执行、决策、回灌和验证组织为可追溯的过程证据；（3）给出可复现的跨生态任务化取证协议与 11 项指标体系；（4）以 CANN/CUDA 案例识别“最弱且最靠前”的知识瓶颈和人机交接风险；（5）提出 DAR 作为从协同轨迹汇总阶段化负荷的可视化工具。本文不将单 Agent 的结果外推为所有模型能力，DAR 的比例参数亦有待通过真实开发者协同实验进一步校准。

**关键词：** Agentic Coding；人机协同开发；大语言模型 Agent；开发者体验；技术知识生态；协同轨迹分析

## 1 引言

AI 辅助编程正在改变开发者进入技术生态的方式。开发者不再总是从导航栏、搜索引擎和文档目录开始，而是将任务目标交给嵌入 IDE、终端或搜索产品中的 AI，由 AI 检索、压缩和组织候选方案。此时，文档、示例、版本矩阵和社区经验既是开发者直接阅读的材料，也是 AI 形成答案的输入。一个页面在人类浏览器中可见，并不代表 Agent 能稳定获取其正文；一段语言流畅的回答，也不代表其命令、版本和前置条件可以在开发者的本机环境中执行。

这带来一个尚未被充分刻画的问题：**开发者与 Agent 如何共同完成开发任务，技术知识生态又如何重塑这种协同？** 仅以模型回答的正确性评价 AI，无法定位失败发生在模型、检索策略、站点工程、知识资产、版本治理还是社区生态；仅以传统开发者体验评价导航和页面，又无法解释为什么开发者在 AI “给出答案”后仍需反复搜索、核对与返工。

本文将技术知识生态定义为支撑开发任务的官方文档、样例、工具入口、版本信息与第三方社区知识的集合。我们提出 DACM：技术知识生态通过 Agent 的证据取得与开发者的现场验证两条相互关联的路径塑造协同过程：（1）它决定 Agent 是否能够获得足够可靠、具体且版本可锁定的证据；（2）它决定开发者在接收 AI 输出后，需要承担多少本机核对、执行、回灌和纠错工作。前者是知识可用性问题，后者是协同机制问题。

为研究该问题，本文使用 CANN 与 CUDA 作为两个具有可比计算开发目标、但知识生态成熟度不同的案例。研究并不比较硬件性能，也不假定两套技术有相同接口；比较的基本单位是开发者要达成的结果，例如安装工具链、定位内存越界、实现并集成自定义算子、运行分布式训练或完成迁移。针对每项结果目标，研究在两个生态中采用真实术语提出对应问题，并按相同检索与记录协议观察 AI 如何寻找、读取、判断并组织知识。

本文回答以下研究问题：

- **RQ1：** 在 Agentic Coding 中，开发者与 Agent 围绕技术知识、本机环境和任务结果形成了哪些协同事件与交接关系？
- **RQ2：** 技术知识生态的发现、读取、内容、版本和社区条件，如何改变 Agent 的建议质量及开发者的接管方式？
- **RQ3：** 多主体协同轨迹能揭示哪些仅看最终回答或页面评分无法观察到的协同断裂？
- **RQ4：** 如何用阶段化、可测量的形式表达 Agent 主导、开发者主导和现场核对负荷，而不将 AI 参与度误作自动化程度？

## 2 相关研究与理论定位

### 2.1 AI 辅助软件开发中的人机协同

现有研究已讨论生成式 AI 对软件开发生产率、代码生成、代码审查与开发者信任的影响。此类工作通常将 AI 视为编程工具或协作者，关注模型输出质量、开发者采纳行为及人类监督。然而，AI 在技术开发中的表现高度依赖外部知识：当任务超出模型训练覆盖或涉及快速演进的专有工具链时，Agent 必须检索官方与社区材料。因而，协同结果不能仅由模型能力解释。

### 2.2 面向 Agent 的知识基础设施

检索增强生成和工具调用研究说明，答案质量取决于检索到的证据及其组织方式。对于技术生态而言，文档的信息架构、服务器渲染方式、版本元数据、可运行示例和社区内容共同决定知识能否被 Agent 发现、抓取、核验和引用。本文将这些供给侧条件统称为“技术知识生态可用性”，强调其既是网站质量，也是协同开发基础设施质量。

### 2.3 从开发者体验到协同体验

开发者体验研究通常考察学习、环境配置、文档查询、开发、调试、支持和进阶等任务旅程。本文继承任务旅程视角，但将 AI 引入开发者与生态之间：AI 可以减少查找与起草的工作，也可能因版本不明、证据不足或无法接触本机事实而制造新的交接成本。由此，本文不把“AI 占比高”解释为更好，而是将 Agent 主导、开发者主导和事实核对负荷作为需要同时观察的变量。

## 3 开发者—Agent 协同机制框架（DACM）

DACM 的目标不是衡量“AI 替代了多少人”，而是解释开发者与 Agent 如何围绕任务推进形成协同机制。图 1 给出其四个组成部分：开发者提出任务目标并承担责任；Agent 从官方、第三方与模型先验中取得证据并组织行动建议；知识生态决定证据能否被发现、读取和核验；本机环境提供版本、硬件、数据、业务约束与真实错误等现场事实。开发者在本机环境中执行、验证和回灌结果，使协同形成循环而非一次性问答。

```text
技术知识生态（官方文档 / 样例 / 版本 / 社区）
                    ↓ 证据取得
          Agent 检索、取证、组织建议
                    ↕ 交接
开发者：目标设定 / 审阅 / 决策 / 责任承担
                    ↕ 执行、回灌、验证
      本机与业务现场（环境 / 硬件 / 数据 / 错误）
                    ↓
             任务完成、返工与信任
```

### 3.1 多主体协同轨迹分析

DACM 通过**多主体协同轨迹分析**落地。它不将时序图视为说明性插图，而将其作为过程数据结构：一个协同轨迹由有序事件构成，每个事件至少记录参与者、动作、知识状态、主导方、交接对象和结果。参与者包括开发者、Agent、官方知识生态、第三方知识生态和本机工具/环境；动作包括检索、读取、起草、执行、决策、回灌与验证；知识状态包括可得、受阻、版本不明、证据冲突与已验证。

这种表示使研究者能够从一次任务中定位最早的知识断裂、统计阶段内的交接密度、追踪不完整证据如何导致后续补搜或返工，并区分“AI 无法取得知识”与“AI 有知识但必须由人读取现场事实”两种根本不同的协同限制。

### 3.2 机制命题

该框架提出两个可检验命题。

- **P1（知识瓶颈命题）：** 当官方、第三方和模型先验均不足时，AI 的任务级支持会显著下降；若瓶颈出现在旅程前段，其影响会沿后续步骤放大。
- **P2（协同验证命题）：** 即使 AI 能提供较完整的步骤，涉及本机环境、版本配套、硬件拓扑、业务数据或验收阈值的任务仍需要开发者承担不可替代的事实核对。

P1 由本研究的检索实测直接观察；P2 由任务类型和协同轨迹进行机制性解释，未来需要通过真实开发者任务观察或实验量化验证。

## 4 研究设计

### 4.1 案例与任务

研究选择 CANN 与 CUDA 作为案例。两者均服务于异构计算开发，但在文档积累、社区规模和模型训练覆盖方面具有不同条件。我们以开发者最终要完成的结果而非 API 名称作为对照基础，共构建 26 个任务，覆盖 7 类工作面：环境与安装（3 项）、算子开发（6 项）、训练（4 项）、推理与部署（4 项）、性能优化（4 项）、调试（2 项）和迁移（3 项）。

每项任务分别编写一对问题，要求两侧达成相同的用户结果、使用各自真实工具和术语、保持答案深度相近。例如，内存越界定位在 CUDA 侧使用 Compute Sanitizer，在 CANN 侧使用 msSanitizer；工具不同，但共同验收目标是定位 kernel/算子中的越界问题。

### 4.2 Agent 任务运行与证据记录

研究固定一个具有实时网页搜索与网页读取能力的 AI Agent，按照统一工作流运行每个问题：检索、记录首个官方结果和关键词改写、读取核心官方页、判断正文可获取性与任务信息充分度、检索第三方来源、记录版本信息、形成回答并判断其版本可锁定性与步骤可复现性。所有任务的检索过程、来源和原始观测被记录在任务日志中，评分由独立脚本根据公开规则计算。

此设计评估的是“固定 Agent 在固定工具条件下对该生态知识的可用性”，并非模型能力排行榜。为了避免把不可见内容臆测为低质量，页面正文无法取得时，该渠道记录为“受阻”；只有可观察证据进入正文详尽度等评分。

### 4.3 指标体系与综合置信度

表 1 概括指标体系。①–④评价官方知识的发现、读取、内容和版本条件；⑤–⑥评价第三方知识的丰富度及可信/一致性；⑦记录模型先验；⑧记录检索成本；⑨–⑩评价答案是否能锁定版本并被照做。每项指标使用可追溯锚点进行 1–5 分编码。

| 环节 | 指标 | 评价问题 |
|---|---|---|
| 官方触达 | 官方可发现性、官方可抓取性 | 核心页面是否能被搜索并取得正文？ |
| 官方质量 | 正文详尽度、版本清晰度 | 是否有命令、参数、前置条件、适用版本与配套关系？ |
| 第三方支撑 | 来源丰富度、可信度/一致性 | 是否有独立、较新且可互证的案例？ |
| Agent 条件 | 模型自带知识、检索成本 | 不检索是否有先验？取证需要多少轮绕行？ |
| 答案产出 | 版本可锁定性、步骤可复现性 | 开发者能否将答案对应到真实环境并照做？ |

综合置信度采用三来源噪声 OR 结构：官方、第三方或模型先验任一来源足够可靠时，均可能为 Agent 提供可用支撑；只有三类来源同时薄弱时，风险才会累积。版本清晰度与检索成本作为修正因子进入计算。该设计避免要求所有来源均强，也避免把同一来源的多项评分简单相加。

### 4.4 开发者侧体验与协同轨迹

为解释检索发现如何进入开发者体验，研究另行对开发者门户开展生命周期取证：沿“找入口和选型、上手、配置环境、编写与查询、编译跑通、调试求助、进阶与生态”分析 24 个触点。触点侧使用 DJFI 指标记录效率、认知、准入、可执行与可发现摩擦。本文不将 DJFI 与 AI 指标混为一个分数；前者描述人类开发者在门户中的基础体验，后者描述 Agent 对任务知识的获得与组织条件。

在算子开发与训练两条场景中，研究将多次检索任务置入开发过程，以 DACM 的事件字段标注 AI 建议、人类决策、本机执行和错误回灌的关系。完整开发过程的线性化呈现是以任务实测为骨架的分析重构，并非 26 项任务均已在真实设备上端到端运行；这一边界将在效度讨论中说明。

## 5 案例发现

### 5.1 RQ1–RQ2：知识生态条件塑造 Agent 的建议起点

26 项任务的对照显示，CANN 任务级综合置信度均值为 0.74，CUDA 为 0.92。该差异不意味着 CANN 在所有任务中均不可用。CANN 在安装、容器、迁移、显存优化、访存优化和概念理解等任务上形成了中高至高的知识支撑；CUDA 在全部 26 项任务中维持高档。由此，AI 可用性更适合被理解为“任务 × 生态 × Agent 条件”的结果，而非一项网站或技术栈的固定属性。

### 5.2 RQ2：深层任务的风险来自多项知识条件叠加

自定义算子开发是最具代表性的低谷。在该任务中，CANN 核心操作 how-to 的正文无法通过被测 Agent 的网页读取链路取得；同时，版本信息分散、第三方内容碎片化、模型先验较薄。CUDA 对照侧则可获得官方教程、示例仓与较厚社区支撑。这里的关键并非将所有页面概括为“SPA 不可读”：全量任务显示，多数 CANN 子树可由静态或服务器渲染页面取得，机器读取障碍集中于少数深层任务页面。这个结果将改造重点从“重做整个网站”收敛为“修复关键任务入口与正文供给”。

版本治理是跨任务出现的系统变量。在若干环境、训练、部署与算子任务中，芯片、驱动、固件、CANN、框架及插件的多轴配套关系分散在不同页面，使 Agent 难以将答案锁定到单一可执行环境。第三方生态和模型先验较薄时，开发者缺少用于交叉验证的替代路径。

### 5.3 RQ3：协同轨迹揭示知识缺口如何转换为人工接管

将检索观察组织为协同轨迹后可以看到，AI 的一次受阻不会停留在“本轮回答质量低”。当最前段的 kernel 编写知识无法被稳定取得时，开发者需要自行拼接资料、判断版本和工程路径；之后的 Tiling、编译、注册集成和精度排查都建立在这些前提之上。轨迹由此呈现传统最终答案评分看不见的现象：较早出现的知识瓶颈会提高后续人机交接中的信息缺失风险，并把 Agent 从起草者推回到解释器或线索提供者。

相较之下，训练场景中的官方知识整体较容易取得，协同轨迹呈现为较均匀的“AI 给方案—开发者按本机事实配置—再验证”循环。训练的困难并未消失，而是更多来自 Agent 无法直接观测的环境事实，例如实际安装版本、卡数、拓扑、显存和数据条件。两条旅程说明：协同体验不应只用平均 AI 可用性概括，任务在生命周期中的位置、知识断裂位置和对现场事实的依赖同样重要。

### 5.4 RQ4：DAR 将协同轨迹汇总为阶段配比，而不是“AI 替代率”

为将协同轨迹压缩为阶段可比的结果图，本文提出开发者—Agent 协同配比（Developer–Agent Ratio, DAR）。对于一个任务阶段 *s*，DAR 使用四个量：

- *A_s*：Agent 主导动作占比；
- *H_s*：开发者主导动作占比；
- *E_s*：阶段总投入（可由时间、动作数或加权交接成本测量）；
- *G_s*：本机/业务事实核对负荷，即必须通过现场配置、执行结果、业务约束或验收标准确认的动作比例。

其中，*A_s + H_s = 1*。图 2 以“协同币”呈现每一阶段：紫色和红色扇面表示 *A_s/H_s*，圆面积表示 *E_s*，金色外环表示 *G_s*。这一定义与简单的自动化率不同：一个阶段可能具有较高的 Agent 主导比例，同时仍有较高的 *G_s*，此时开发者必须保持验证角色，不能将工作直接无人值守地交给 Agent。

本文现阶段将 DAR 作为**描述性汇总图与测量方案**，而非已由大规模样本估计的普适比率。案例图中的比例应被视作根据协同轨迹动作编码得到的原型；后续研究需记录真实协同会话、操作日志与开发者耗时，以计算并检验 DAR 的稳定性。

## 6 讨论：技术知识生态应成为协同开发基础设施

### 6.1 从“文档好不好看”到“知识是否可被可靠地行动化”

当 Agent 成为开发入口，文档优化不能只以可读性或导航完成度为目标。一个高质量任务知识单元至少需要同时向人和 Agent 提供：可发现的入口、可读取的正文、可执行的命令/代码、明确的前置条件、版本和兼容范围、预期结果、常见失败及下一步。这样的资产不仅提高 AI 检索质量，也降低开发者接受 AI 建议后的核对成本。

### 6.2 供给侧与使用侧的双重改造

供给侧的优先级应按任务风险而非页面数量确定：优先修复最前段、最深层且缺乏替代来源的任务；收口跨页面版本关系；为核心操作页提供稳定、机器可读的正文和完整样例；培育独立而可互证的社区案例。使用侧则应把人机交接作为产品能力：AI 应明确其证据来源、版本假设和待用户补充的现场事实；开发工具应支持完整回灌报错、环境快照与验证结果，而非仅让用户复制一段回答。

### 6.3 DAR 的适用边界

DAR 不是预测某职业会被 AI 替代的比例，也不是将开发者价值压缩为剩余人工时间。它服务于三个更具体的问题：哪些阶段适合让 Agent 主导起草或检索；哪些阶段需要把验证前置；知识生态或工具改造是否确实降低了人工接管；不同任务、不同模型和不同经验水平的协同结构如何变化。与“人/AI 谁贡献更多”的静态比值相比，DAR 强调协同配比会随任务阶段和现场事实而变形。

## 7 效度威胁与研究局限

**构念效度。** 11 项指标依赖预先定义的锚点与聚合规则；尽管原始观测、计算脚本与评分逻辑可追溯，指标仍不能覆盖信任、情绪、组织协作等主观体验。DAR 的 *A_s/H_s/E_s/G_s* 在当前版本中是测量提案，尚未经过大样本信度或效度检验。

**内部效度。** AI 可用性结果来自一个固定 Agent、特定检索工具与评估时点。模型、搜索排序、网页可访问性和站点内容变化都可能改变结果。部分任务由并行 Agent 运行后再统一清洗与评分，尽管保留了过程记录，仍可能引入执行差异。

**外部效度。** CANN/CUDA 是具有代表性的计算开发案例，但不能代表所有 SDK、语言或行业。任务集覆盖 26 个常见目标，却不能穷尽开发工作。后续应至少扩展到一个额外生态，并采用多个 Agent 与重复运行评估鲁棒性。

**生态与用户效度。** 门户触点基于真实页面取证与任务分析，并非大样本终端用户研究。协同开发旅程中关于端到端执行、交接次数和主导权的部分属于基于检索证据的合理重构；要验证其对完成时间、返工、信任和成功率的影响，需要补充真实开发者的受控任务实验或现场研究。

## 8 结论

本文研究了 Agent 参与开发后，技术知识生态如何同时影响 AI 作答与开发者执行。通过 26 项 CANN/CUDA 对照任务、统一取证协议和开发旅程分析，研究显示 AI 可用性是任务相关的：上手、迁移和部分训练任务可获得较好支撑，而深层专有开发知识更容易遭遇机器读取、版本治理、社区互证和模型先验的叠加缺口。此类缺口并非只降低一次回答的分数，还会把开发者推入更多搜索、判断、执行与回灌。

本文提出 DACM，将开发任务看作开发者、Agent、知识生态与本机现场持续交接的过程；并以多主体协同轨迹分析识别其中的知识断裂、主导权迁移和人工接管。DAR 作为该过程的阶段化汇总表达，呈现 Agent 主导、开发者主导、总投入和现场核对负荷。DACM 的核心立场是：高 AI 参与不等于低人工责任；只要本机与业务事实仍不可被 Agent 充分获得，开发者就必须保留验证与决策位置。未来工作将以真实开发者协同观察或实验校准 DAR，检验知识生态改造能否减少人工接管，并将 DACM 扩展到更多技术生态与 Agent 系统。
