# DACM 协同开发情境推演方案（CHI v0.2）

## 1. 与访谈的分工

本研究不以统一算卡为前提，采用“真实项目回放访谈 + 统一算子开发情境推演”的组合。

| 环节 | 要回答的问题 | 主要数据 |
|---|---|---|
| 真实项目回放访谈 | 真实工作中，开发者与 Agent 如何分工、交接、回灌与验证？ | 录音；自愿提供的对话、终端、代码 diff、PR、文档访问；共同绘制的轨迹 |
| 统一情境推演 | 不同知识条件下，开发者如何与 Agent 形成下一步实施和验证计划？ | Agent 对话、资料访问、过程记录、书面计划、简短回放 |

真实回放是 CHI 的主数据；情境推演提供可比较的对照轨迹。两者均不要求参与者提供私有源码。

## 2. 参与者与流程

- 目标样本：20 名有 AI Coding 使用经验的开发者；记录 Python/PyTorch/CUDA/CANN 等背景，但不以拥有算卡为招募条件。
- 每人完成一次真实项目回放和两份算子开发情境包；情境包顺序采用 AB/BA 平衡，每份约 20 分钟。
- 固定使用一种具备检索能力的 AI 助手；允许使用指定的官网、文档与公开社区，禁止向他人求助。
- 推荐流程：知情同意（5 分钟）→ 背景问卷（5 分钟）→ 真实项目回放（35–45 分钟）→ 情境 A（20 分钟）→ 短问卷（3 分钟）→ 情境 B（20 分钟）→ 回放访谈（15–20 分钟）。
- 单人总时长：约 100–120 分钟。

## 3. 为什么给情境包，而不要求真实算卡

情境包应提供预置代码与可读环境材料，而不要求参与者从零开始或实际访问算卡。否则系统权限、网络、个人环境、安装时长与算卡可用性会成为主要变量，遮蔽本研究真正关心的协同机制。

```text
scenario-a-or-b/
  README.md                # 任务目标、可用资源、交付格式；不提供答案
  starter/                 # 最小工程骨架；不要求实际运行
  evidence/                # 官方页、版本矩阵、样例、社区材料入口/快照
  logs/                    # 一段编译或运行日志，用于识别待补现场信息
  environment-manifest.md  # 可发现但不前置展示的版本、设备与依赖信息
  response-template.md     # “下一步实施与验证计划”模板
```

情境应保留少量必须从“现场”取得的事实，例如实际版本、设备/卡数、报错全文、输入 shape 或验收阈值。参与者必须发现并把这些事实列入对 Agent 的追问或验证计划；这使研究能够观察现场核对负荷，而非做纯文档问答。

## 4. 两个统一算子开发情境

### 情境 A：首个算子跑通——知识链连续

**任务目标：** 在给定 Ascend C `AddCustom` 脚手架中，形成从 kernel 实现、编译到数值验证的下一步实施计划。

**材料：**

- `AddCustom` 工程骨架、输入输出约束与目标验收；
- 连续且可读的官方教程/样例入口；
- 一份版本较清晰的环境清单；
- 一段需要理解、但不妨碍规划的编译/运行输出。

**参与者交付：** 使用 Agent 形成实施与验证计划，写出准备修改的文件、需要确认的版本/环境事实、引用的资料、预期验证命令和仍不能确认的风险。

**观察：** Agent 是否主导检索和起草；开发者是否主动读取环境；现场事实怎样回灌给 Agent；“一般正确建议”如何被具体环境修正。

### 情境 B：让算子真正可用——知识链断裂/拼接

**任务目标：** 在已能运行静态 `AddCustom` 的基础上，计划支持一组动态 shape，或注册并接入 PyTorch/torch_npu。

**材料：**

- 已能运行的静态 shape 工程片段；
- 动态 shape / Tiling / 注册接口的跨文档材料入口；
- 多版本并存、样例不完整或关键正文不易取得的真实知识条件；
- 一段编译/调用日志与未展开的环境信息。

**参与者交付：** 使用 Agent 形成实施与验证计划，标出无法凭现有材料确认、必须回到真实环境验证的事项。

**观察：** Agent 资料不足、建议不完整或版本不明时，开发者如何转向官网/社区、修改问题、补充日志、接管规划，并显式标注验证边界。

> 情境推演不替代真实 Ascend 端到端体验。它可以研究知识协同与验证决策；论文不得将其结果表述为 CANN 算子开发的完成率、性能或真实环境摩擦。

## 5. 参与者看到的情境卡

```text
情境名称：规划一个可验证的算子开发下一步

目标：基于所给工程与资料，为下一步实现和验证形成具体计划。
可用工具：指定 AI 助手、浏览器、终端/文本材料、官方文档与公开社区。
限制：不直接向他人求助；不假设你能访问未提供的算卡环境。
完成条件：提交实施/验证计划，并标明资料来源、待确认现场信息与风险。
时间：20 分钟；请保留与 Agent 的全部对话和访问过程。
```

## 6. 采集与研究者观察

保存：Agent 对话的完整导出或截图序列、参与者的实施/验证计划与引用来源、访问的官方/社区页面 URL 与时间戳、每阶段起止时间和资料切换。

研究者可记录事件标记，但不应在任务中提示“你现在正在被编码”。关键事件包括：首次向 AI 提问、首次访问外部来源、首次提出现场信息需求、向 AI 回灌现场事实、人工接管、形成验证 checkpoint、停止。

## 7. 任务后的最小量表

每个情境后 1–7 分回答：

1. 我知道 AI 建议基于哪些证据。
2. 我知道下一步哪些信息必须由我核对。
3. 我对当前实施计划是否可靠有把握。
4. 我在任务过程中保持了控制感。
5. 若可访问真实环境，我知道如何继续验证这份计划。

这些是探索性过程测量；若用于后续 IJHCS，应以文献为依据补充或替换为已验证量表。

## 8. 伦理与数据保护

- 真实项目回放不要求交出源码；参与者可只分享脱敏对话、截图、diff 或口述。
- 录音、屏幕与对话采集需单独获得同意；参与者可在访谈后标记删除片段。
- 论文使用匿名编号，删除路径、账号、token、内部域名及可识别业务信息。
- 情境包不应含内部资料、账号或密钥；公开资料快照应记录来源与访问日期。
