# DACM 受控实作测试方案（v0.1）

## 1. 目的与访谈的分工

本研究将“实作测试”与“任务后访谈”分开。

| 环节 | 要回答的问题 | 主要数据 |
|---|---|---|
| 受控实作测试 | 开发者和 Agent 实际如何分工、交接、回灌与验证？ | 屏幕、Agent 对话、终端、网页访问、代码提交、耗时、结果 |
| 任务后访谈 | 开发者为什么信任、拒绝或接管？如何理解社区的角色变化？ | 录音、任务回放、半结构化追问 |

实作测试是 DACM / DAR 的主数据；访谈用于解释轨迹中不能从操作本身看出的意图与判断。

## 2. 参与者与总体流程

- 目标样本：20 名有 Python、PyTorch 或相关 AI 开发经验的开发者。
- 每人完成 2 个任务，顺序采取 AB/BA 平衡；每个任务 25–30 分钟。
- 固定使用同一种具备检索能力的 AI 助手；允许使用指定的官网、文档与社区，禁止向他人求助。
- 推荐流程：知情同意（5 分钟）→ 背景问卷（5 分钟）→ 任务 A（30 分钟）→ 短问卷（5 分钟）→ 任务 B（30 分钟）→ 任务后访谈（20–30 分钟）。
- 单人总时长：约 95–115 分钟。

## 3. 为什么应提供预置代码与环境

应提供，而非让参与者从零开始。否则系统权限、网络、个人环境和安装时长会成为主要变量，遮蔽本研究真正关心的协同机制。

每个任务包固定包含：

```text
task-a-or-b/
  README.md                # 任务目标、允许资源、验收命令；不提供答案
  starter/                 # 可运行但不完整/含故障的最小项目
  tests/                   # 隐藏或公开的验收脚本
  logs/                    # 至少一条初始报错或运行输出（按任务决定是否提供）
  environment-manifest.md  # 可发现但不前置展示的版本、设备与依赖信息
  capture/                 # 自动保存命令、时间戳、结果的脚本
```

任务应保留少量必须从“现场”取得的事实，例如实际版本、设备/卡数、报错全文、输入形状或验收阈值。参与者必须发现并把这些事实提供给 Agent；这才可测量 DAR 中的现场核对负荷，而不是把实验做成纯文档问答。

## 4. 推荐的两类任务

### 任务 A：知识可取得、但仍需现场核对的环境/训练任务

**候选主题：** 给定一个最小 PyTorch 训练工程，将单卡脚本改为预置的双卡/模拟分布式配置，或完成 CANN/torch_npu 版本兼容核对并使脚本跑到指定输出。

**给参与者的材料：**

- 可启动的最小训练仓；
- 一份失败的启动脚本或错误的配置项；
- 本机/容器中可查询的版本、卡数、环境变量；
- 官方文档和社区访问权限。

**验收：** 脚本通过指定 smoke test，输出预期的 world size/设备信息或完成若干步训练。

**要观察：** Agent 是否能主导检索和起草；开发者是否主动读取版本/环境；环境事实怎样回灌给 Agent；AI 的“正确一般建议”怎样被现场配置修正。

### 任务 B：知识较脆弱、交接密集的代码/调试任务

**候选主题：** 给定一段可编译但输出错误、或带有明确内存/shape/注册问题的最小算子/扩展工程，要求定位并修复一个故障，使测试通过。

**给参与者的材料：**

- 有 1–2 个可定位故障的最小工程，而非从零写算子；
- 初始失败用例、可查看的编译/运行日志；
- 可搜索的官方资料与社区；
- 固定版本与硬件模拟/远程环境，避免环境搭建占时。

**验收：** 指定单元测试通过，并由隐藏测试排除“硬编码输出”等投机修复。

**要观察：** 当 Agent 资料不足、建议不完整或版本不明时，开发者如何转向官网/社区、修改问题、补充日志、接管实现和验证结果。

> 如果真实 Ascend 环境暂不可稳定提供，任务 B 的第一版可采用 PyTorch C++/CUDA 扩展或可运行的模拟工程，以验证 DACM 方法；但不应把“模拟环境”得出的结果写成 CANN 体验结论。CANN 专属比较需在可控 Ascend 环境中单独完成。

## 5. 任务卡应如何写

参与者只应看到结果目标和必要边界，不应看到研究假设、任务类型或知识条件标签。

```text
任务名称：让给定工程通过验收

目标：修复 starter/ 中的问题，使 `bash verify.sh` 通过。
可用工具：指定 AI 助手、终端、浏览器、官方文档与公开社区。
限制：不直接向他人求助；不更换基础依赖的大版本；可以修改工程文件。
完成条件：verify.sh 显示 PASS，并简要说明你如何验证。
时间：30 分钟；未完成也请停在当前状态并保留过程。
```

## 6. 自动采集与研究者观察

必须自动保存或统一记录：

- Agent 对话的完整导出或截图序列；
- 终端命令、标准输出与错误输出；
- 代码差异与测试结果；
- 访问的官方/社区页面 URL 与时间戳；
- 每阶段起止时间。

研究者可记录事件标记，但不应在任务中提示“你现在正在被编码”。关键事件包括：首次向 AI 提问、首次访问外部来源、首次执行、首次失败、向 AI 回灌现场事实、人工接管、成功验证、停止。

## 7. 任务后的最小量表

每个任务后 1–7 分回答：

1. 我知道 AI 建议基于哪些证据。
2. 我知道下一步哪些信息必须由我核对。
3. 我对当前结果是否正确有把握。
4. 我在任务过程中保持了控制感。
5. 若再次遇到同类任务，我愿意采用类似协作方式。

这些条目目前是探索性过程测量，正式用于 IJHCS 前需结合文献确定或替换为已验证量表。

## 8. 伦理与数据保护

- 任务工程不得包含参与者的真实工作代码、账号或密钥。
- 录屏、对话与终端采集需单独获得同意；参与者可在访谈后标记删除片段。
- 论文使用匿名编号，日志删除路径、账号、token、内部域名及可识别业务信息。
- 若使用真实 CANN/Ascend 环境，需事先说明远程环境日志和命令可能被系统保留的范围。
